# 관리자 기능 규칙

대상: `app/admin/**`, `app/api/admin/**`

## 권한

- 관리자 경로는 기본 차단, 명시적 허용 방식으로 보호한다.
- 권한 검사는 **서버에서** 한다. 화면에서 메뉴를 숨기는 것은 보호가 아니다.
- API Route마다 권한을 확인한다. 레이아웃 검사에 의존하지 않는다.
- 역할: `STAFF`(견적 조회·상태 변경), `ADMIN`(가격 규칙 변경). 가격 규칙 쓰기는 `ADMIN`만 가능하다.
- **현재 구현된 역할은 `ADMIN` 하나뿐이다.** 공유 비밀번호 + 서명 쿠키이고, 권한 판단은 `src/lib/auth.ts` 한 곳에만 있다. (ADR-0011)
  인증 방식을 바꿀 때 그 파일 밖을 고쳐야 한다면 설계가 샌 것이다.
- 로그인은 **시도 횟수를 제한한다.** 같은 IP 5회 / 전체 20회(10분 창)에 닿으면 비밀번호를 비교하지 않고 `429`. (ADR-0020)
  한도·창 길이는 `src/services/admin/login-throttle.ts`의 상수이고, 판정은 그 파일의 순수 함수 하나뿐이다.
  응답에 **남은 시도 횟수를 넣지 않는다.** 잠금 사실과 남은 시간만 알려준다.
  요청자 IP 는 `src/lib/client-ip.ts` 가 정하고, **`CF-Connecting-IP` 하나만 읽는다.** (ADR-0024)
  `x-forwarded-for`·`x-real-ip` 는 읽지 않는다. Cloudflare 는 전자를 덮어쓰지만 후자들은
  클라이언트 값 뒤에 덧붙이므로 맨 왼쪽을 공격자가 고를 수 있다. 대체 경로를 만들면
  제한은 가장 약한 경로의 강도가 된다. 헤더가 없으면 `"unknown"` 한 칸으로 모은다.
  그래도 IP별 한도만으로 끝내지 않는다. 전체 한도가 분산 시도의 안전망이다.
- 미들웨어는 Edge 런타임이라 서명을 검증할 수 없다. 쿠키 **존재**만 보는 1차 방어이고, 실제 판단은 각 Route·페이지에서 `isAdmin()`으로 다시 한다.
  이 때문에 미들웨어는 `node:crypto`를 끌고 오는 모듈을 import 하면 안 된다. 쿠키 이름은 `src/lib/auth-cookie.ts`에 따로 둔다.

## 가격 규칙 변경

- 수정은 덮어쓰기가 아니라 새 버전 추가다. (ADR-0002)
- 저장 화면에는 `effectiveFrom` 입력이 반드시 있다. 비워 두면 즉시 적용으로 처리한다.
- **같은 대상에 같은 `effectiveFrom` 버전을 두 번 넣을 수 없다.** 버전 테이블의 유일 제약
  (`[groupId, code, effectiveFrom]`, `[productId, code, effectiveFrom]`)이다. 화면 입력이 분 단위라
  실제로 부딪히므로 Repository 가 미리 확인해 사유를 던지고 Route 는 `400` 으로 돌려준다.
  제약 위반(P2002)을 그대로 흘려 `500` 으로 만들지 않는다.
- 저장 전에 **샘플 입력으로 계산 미리보기**를 제공한다. 미리보기는 `/api/estimate`와 동일한 Service를 호출한다. 별도 계산 로직을 만들지 않는다.
- 할인 조건에 넣은 옵션 코드가 그 상품에 실제로 존재하는지 서버에서 검증한다. 통과하지 못하면 저장하지 않는다. (ADR-0009)
- 옵션을 비활성화할 때 그 옵션을 조건으로 쓰는 할인은 **같은 트랜잭션에서 함께 끈다.** 경고로 끝내지 않는다.
  조건 옵션이 꺼진 할인을 남기면 `findRuleSet`이 조건을 해석하지 못해 그 상품 계산이 통째로 실패한다. (ADR-0017)
- **할인 비활성화는 그 할인만 끈다.** 조건 옵션은 건드리지 않는다. (ADR-0026) 옵션 비활성화의
  역방향이 아니다. 거기서는 조건을 해석할 수 없어서 끌 수밖에 없었고, 여기서는 할인만 빼는 것이다.
  같은 코드의 **모든 버전 행**을 끄고 삭제하지 않는다. 과거 견적의 스냅샷이 이 코드를 가리킨다.
  되돌리는 길은 재활성화가 아니라 새 버전 등록이다. 끄기 전에 그 할인의 조건과 할인율을 보여준다.
- 변경 요약(무엇이 이전값 → 새값)을 저장 직전에 확인시킨다.

## 옵션 생애주기 (ADR-0023)

- **신규 옵션은 기존 그룹 안에만 만든다.** 그룹 신설·`singleSelect`·`required`·`dependsOnGroupId`를
  이 화면에서 편집하지 않는다. 그룹 구조는 상품 설계이고 금액 운영이 아니다.
  그룹 **신설**은 `상품 설계` 절이 담당한다. (ADR-0046) 이 금지는 **금액 운영 폼에 한정된다.**
  기존 그룹의 구조를 **수정**하는 길은 어느 화면에도 없다.
- 같은 그룹에 같은 `code`가 **비활성으로라도** 있으면 신규 등록을 거부한다. 되살리는 길은 재활성화 하나다.
- **옵션 `code`는 불변이다.** 할인 조건이 코드로 옵션을 가리킨다(ADR-0009). 바꿀 수 있는 것은 이름과 금액뿐이고,
  둘 다 새 버전 행 `INSERT`로 바꾼다. 이름만 바뀌는 저장도 버전을 남긴다.
- **재활성화는 비활성화의 정확한 역이다.** 그 코드의 모든 버전 행을 켜고, 함께 꺼진 할인을 되살린다.
  단 **조건 옵션이 전부 활성이 되는 할인만** 켠다. 아직 꺼진 조건이 남은 할인은 끈 채로 두고 사유를 보여준다.
- 되살아날 할인과 그대로 꺼져 있을 할인을 **저장 전에 모두 보여주고** 확인받는다.
- 되살릴 수 있는지 판정하는 조건문을 화면과 서버에 따로 적지 않는다.
  `src/repositories/option-revival.ts`의 순수 함수 하나를 양쪽이 쓴다.
- 금액 버전 추가는 **활성 옵션만** 대상으로 한다. 꺼진 옵션에 버전을 넣어 조용히 되살리는 경로를 만들지 않는다.
- 신규 등록·재활성화에는 계산 미리보기를 붙이지 않는다. 비교할 이전값이 없다. 금액 **수정**에는 붙인다.

## 상품 생애주기 (ADR-0046)

- 상품(상위 탭) 신설·그룹 신설·상품 활성화는 **`상품 설계` 절**에서 한다. 금액 운영 폼과
  같은 자리에 두지 않는다. 구조를 만드는 일과 숫자를 고치는 일이다.
- **새 상품은 `isActive: false` 로 만든다.** 폼에 활성 여부 입력을 두지 않는다.
  **활성 옵션이 하나도 없는 상품은 켜지지 않는다.** 서버가 사유와 함께 거부한다.
  빈 탭은 눌러도 고를 것이 없고 0원으로 계산된다. 화면에서 막는 것이 아니라 켜지지 않게 막는다.
- 상품 `code` 는 옵션 코드와 같은 형식(`^[A-Z][A-Z0-9_]*$`)이고 **불변이다.**
  비활성으로라도 같은 코드가 있으면 거부한다. 이름은 한글이고 코드와 같은 값으로 받지 않는다.
  **상품 이름 수정은 범위 밖이다.** 과거 견적이 상품명을 관계로 읽어서 소급 적용된다.
- `sortOrder` 를 받지 않는다. 새 상품·새 그룹은 **맨 뒤**다. 자리는 표시 순서 화면이 옮긴다.
  (ADR-0026) 신설 폼에서 자리 번호를 또 받으면 같은 값을 두 화면이 쓴다.
- 그룹 신설의 선행 관계는 **같은 상품의 이미 있는 그룹**만 가리킨다. (ADR-0010)
  `dependsOnOptionCode` 는 그 선행 그룹에 실제로 있는 코드여야 하고,
  **`dependsOnGroupId` 없이 코드만 넣을 수 없다.** (ADR-0044)
  `selectAll` 과 `singleSelect` 를 함께 켤 수 없다. (ADR-0043)
- **안내 전용 단계(`noticeOnly`)는 고를 것이 없는 단계다.** (ADR-0048) 이름과 설명만 보이고
  금액에 들어가지 않는다. 네 가지를 함께 막는다. 옵션을 넣을 수 없고, `required` ·
  `selectAll` 을 켤 수 없고, **다른 단계의 선행 단계로 고를 수 없다.**
  선택이 생길 수 없어서 가리킨 단계가 영구히 잠긴다. (ADR-0010)
  이 판정을 화면에만 두지 않는다. Zod 가 조합을, Repository 가 관계를 본다.
  설명 입력은 이 폼에 두지 않는다. 만든 뒤 `설명 문구` 에서 채운다. (ADR-0025)
  비어 있으면 이름만 보이므로 폼이 그 사실을 적는다.
- 새 그룹은 선행 그룹보다 아래에 생기므로 ADR-0026 의 "선행보다 위에 둘 수 없다" 가 저절로 지켜진다.
- **상품 삭제는 없다.** `QuoteItem` 이 상품을 가리킨다. 비활성화만이다.
- **상품 비활성화는 연쇄가 없다.** 그 상품의 그룹·옵션·할인·묶음을 건드리지 않는다.
  `findRuleSet` 이 `isActive: true` 로 상품을 찾으므로 꺼진 상품은 계산이 들어오지 않는다.
  ADR-0017 이 연쇄를 요구한 것은 같은 상품 안에서 할인 조건이 해석되지 않는 경우였다.
- 활성화 가능 여부 판정을 화면과 서버에 따로 적지 않는다. 순수 함수 하나를 양쪽이 쓴다.
- **관리자 화면은 비활성 상품도 읽는다.** 금액 운영 탭과 표시 순서 목록에 함께 넣고
  꺼진 탭에 `꺼짐` 을 적는다. 활성만 읽으면 방금 만든 상품에 옵션을 넣을 길이 없고,
  옵션이 없으면 켤 수 없어서 막다른 상품이 된다. 좁히는 것은 고객 화면(`findRuleSet`)뿐이다.
- 신설·활성화·비활성화는 `PRODUCT_CREATED` · `PRODUCT_GROUP_CREATED` ·
  `PRODUCT_ACTIVATED` · `PRODUCT_DEACTIVATED` 로 남긴다. 활성화와 비활성화를 한 값으로
  묶지 않는다. 목록에서 방향이 바로 읽혀야 한다.
- 계산 미리보기를 붙이지 않는다. 상품·그룹은 금액을 만들지 않는다.
- **비활성 상품도 이 절의 목록에 보인다.** 보이지 않으면 방금 만든 상품을 켤 수 없다.

## 설명 문구 (ADR-0025)

- 단계(그룹) 설명과 옵션 설명을 이 화면에서 편집한다. 저장은 **덮어쓰기**다.
  새 버전을 만들지 않는다. 설명은 금액이 아니라 현재 안내문이고, 문구 수정이
  가격 버전 행을 쌓으면 금액 이력을 읽을 수 없게 된다.
- **계산 미리보기를 붙이지 않는다.** 설명은 계산에 들어가지 않는다.
- **빈 값 저장을 허용한다.** 지우면 화면에서 사라지고 그것이 정상 상태다.
- 옵션 설명의 대상은 `(groupId, optionCode)` 다. 금액 버전을 추가해도 설명은 그대로 따라온다.
- 올스토리 단계의 **상담 제목은 한 줄 설명(`summary`)에 있다.** (ADR-0031) 이름은
  `1단계 (60~80분)` 까지다. 제목 수정은 문구 운영이고 **확정 견적서에 반영되지 않는다.**
  설명은 스냅샷이 아니기 때문이다. 금액의 한정(`첨삭 제외` 등)은 설명이 아니라
  **이름**이다. 견적서에 남아야 하므로 설명 칸에 적지 않는다. (ADR-0028)
- 그룹 구조(`singleSelect`·`required`·`dependsOnGroupId`)는 여기서도 편집하지 않는다.
  설명 편집은 문구 운영이고 그룹 구조는 상품 설계다. (ADR-0023과 같은 선)

## 표시 순서 (ADR-0026)

- 상품 탭 순서, 단계(그룹) 순서, 단계 안 옵션 순서를 이 화면에서 바꾼다. 저장은 **덮어쓰기**다.
  `effectiveFrom` 을 받지 않고 새 버전 행을 만들지 않는다. 순서는 금액이 아니라 화면 배치라서
  과거 견적의 근거에 들어가지 않는다.
- 요청은 **그 묶음의 전체 순열**로 받는다. "한 칸 위로" 단건 API 를 만들지 않는다.
  동시 편집에서 서버가 읽은 순서가 낡으면 둘 중 어느 쪽도 아닌 결과가 된다.
- 화면은 각 줄에 **자리 번호를 입력**받는다. `↑` `↓` 버튼도 드래그도 두지 않는다. (ADR-0032)
  `1 ~ N` 이 빠짐없이 한 번씩이어야 저장이 열리고, 빈 칸을 추측해 채우지 않는다.
  판정은 `src/lib/order-input.ts` 의 순수 함수 하나이고 화면이 조건문을 직접 적지 않는다.
  번호를 고쳐도 **줄은 제자리에 두고** 결과는 미리보기로 보여준다. 입력 칸이 커서 아래에서
  움직이면 어느 줄을 고치던 중인지 놓친다.
- 서버는 **구성원이 빠짐없이 정확히 한 번씩** 들어 있는지만 검증하고 `sortOrder = index` 로 다시 매긴다.
  누락·중복·그 묶음 밖 항목은 `400` 이다.
- 옵션 순서는 그 코드의 **모든 버전 행**에 같은 값을 쓴다. 유효한 행에만 쓰면 금액 버전을
  추가한 순간 원래 자리로 돌아간다. (ADR-0023 의 `isActive` 와 같은 방식)
- 순서 변경은 `DISPLAY_ORDER_CHANGED` 로 이전 순서 → 새 순서를 남긴다.
- 계산 미리보기를 붙이지 않는다. 순서는 계산에 들어가지 않는다.
- 비활성 옵션도 목록에 보이지만 순서 대상에 함께 넣는다. 되살렸을 때 자리가 유지돼야 한다.
  **비활성 상품도 같다.** (ADR-0046) 화면이 보내는 목록과 서버가 읽는 현재 순서의 범위가
  어긋나면 전체 순열 검증이 통과하지 못해 순서를 아예 바꿀 수 없게 된다.
- **단계를 선행 그룹(`dependsOnGroupId`)보다 위에 둘 수 없다.** 서버가 사유와 함께 거부한다.
  선행이 충족되지 않은 그룹은 `disabled` 로 그려지므로(ADR-0010), 위에 두면 화면 맨 위가
  "먼저 아래 항목을 선택하세요" 로 시작한다. 고르는 순서를 거꾸로 읽히게 만드는 배치다.
- 그룹 구조(`singleSelect`·`required`·`dependsOnGroupId`)는 여기서도 편집하지 않는다. (ADR-0023과 같은 선)

## 묶음 관계 (ADR-0038)

- 상품 탭 안에서 묶음 옵션과 구성 옵션을 골라 **추가**하거나 기존 관계를 **삭제**한다.
  수정은 없다. 구성 하나를 바꾸는 것은 지우고 다시 넣는 것이다. 상품 코드로 분기하지 않는다.
- 저장은 가격 버전이 아니다. `effectiveFrom` 을 받지 않는다. 묶음 관계는 금액에 들어가지
  않고 과거 견적의 근거도 아니다. (ADR-0037)
- 서버가 검증한다. 통과하지 못하면 `400` 이다.
  - 묶음 옵션·구성 옵션은 그 상품에 실제로 있는 코드여야 한다.
  - 구성 옵션은 **2개 이상**이고, 묶음 옵션 자신이 구성에 들어갈 수 없다.
  - 같은 묶음 옵션에 관계를 두 번 넣을 수 없다. 유일 제약 위반(P2002)을 그대로 흘려
    `500` 으로 만들지 않는다.
- **묶음이 더 싼지는 검증하지 않는다.** 안내 여부는 계산 시점의 두 총액 차이가 정한다.
  저장 시점 금액으로 막으면 금액이 바뀌었을 때 기준이 둘이 된다. (ADR-0037)
- **비활성 옵션도 고를 수 있다.** 꺼진 옵션의 묶음은 안내가 뜨지 않을 뿐이고 되살리면 돌아온다.
- 계산 미리보기를 붙이지 않는다. 묶음 관계는 계산에 들어가지 않는다.
- 추가·삭제는 `BUNDLE_ADDED` · `BUNDLE_REMOVED` 로 남긴다.

## 이력과 감사 로그

다음 작업은 `누가 · 언제 · 무엇을 · 이전값 → 새값`을 기록한다.

- 가격 규칙 생성·버전 추가·비활성화
- 견적 상태 변경
- 견적 금액 수동 조정 (허용되는 경우)
- 개인정보가 포함된 데이터 내보내기 (`QUOTE_EXPORTED`)
- 설명 문구 수정 (`DESCRIPTION_UPDATED`)
- 표시 순서 변경 (`DISPLAY_ORDER_CHANGED`)
- 할인 비활성화 (`DISCOUNT_DEACTIVATED`)
- 견적 숨기기·되돌리기 (`QUOTE_HIDDEN` · `QUOTE_RESTORED`)
- 견적 삭제 (`QUOTE_DELETED`)

감사 로그는 수정·삭제하지 않는다. 기록과 본 작업은 같은 트랜잭션에서 수행한다.
삭제 로그에는 `publicId` 와 상품·금액만 적고 **연락처를 담지 않는다.** (ADR-0041)
파기한 데이터를 로그로 되살리면 지운 뜻이 없어진다.

## 견적 관리

- `CONFIRMED` 견적의 금액·선택 내역을 수정하는 UI를 만들지 않는다. "복제해서 새 견적" 동작만 제공한다.
- 상태 전이는 `docs/architecture.md` 6절의 경로만 허용한다. 임의 상태 지정 API를 만들지 않는다.
- **고객 연락처를 가리지 않는다.** (ADR-0047) 목록도 상세도 이름과 휴대폰을 그대로
  보여준다. 관리자 경로 전체가 로그인 뒤에 있고(ADR-0011), 전화를 걸 사람이 보는 화면이다.
  마스킹 함수를 되살리지 않는다. 휴대폰은 `formatPhone` 으로 하이픈만 넣는다.
  **열람 로그(`QUOTE_VIEWED`)는 상세 화면에만 남긴다.** 목록은 페이지마다 호출되므로
  거기에 남기면 감사 로그가 목록 열람으로 덮여 특정 고객을 누가 봤는지 찾을 수 없게 된다.
- 상태 되돌리기(`CONFIRMED`·`CANCELED` → `REQUESTED`)는 허용한다. (ADR-0034) 확인 문구에
  **"되돌릴 수 없습니다" 를 쓰지 않는다.** 경고가 사실과 다르면 다음부터 읽히지 않는다.
  확정을 떠나는 전이는 `confirmedAt` 을 비운다. 보존기간의 기준이 어긋나기 때문이다. (ADR-0022)
- 정리의 기본은 `hiddenAt` 으로 숨기는 것이다. (ADR-0035) 숨김은 `status` 와 직교한다.
  숨겨도 상태는 그대로이고, 되돌리면 **같은 `publicId` 가 다시 열린다.**
  숨긴 견적은 **고객 링크도 닫힌다.** 관리자가 보지 않는 견적이 고객 화면에 살아 있으면
  고객이 고른 결제 방식을 받을 사람이 없다. (ADR-0033)
  목록·검색은 기본적으로 숨긴 견적을 제외한다. **되돌리기는 상세 화면에서** 한 건씩 한다.

### 목록 일괄 작업 (ADR-0041)

- 목록 각 줄 앞에 체크박스를 두고, 고른 건을 하단 버튼으로 처리한다.
  **숨기기**는 모든 상태에 쓸 수 있고 되돌릴 수 있다. **삭제**는 `REQUESTED` · `CANCELED` 만이고
  행을 실제로 지우며 되돌릴 수 없다.
- **`CONFIRMED` 가 하나라도 섞이면 아무것도 지우지 않고** 어느 건이 문제인지 적어 거부한다.
  일부만 지우면 운영자는 전부 지웠다고 읽고 넘어간다. 확정 건은 5년 보존 대상이다. (ADR-0022)
- **전체 선택은 버튼이고, 그 선택으로는 지울 수 없다.** (ADR-0049) ADR-0041 이 전체 선택
  체크박스를 금지한 이유는 입력 하나가 20건을 고르게 만들면 지울 생각이 없던 건이 선택에
  들어온 것을 읽지 못하기 때문이다. 그 위험은 `삭제` 에서 오므로 둘을 끊는다.
  - `<button type="button">` 이고 눌린 모양도 켜진 모양도 없다. `aria-pressed` 를 붙이지
    않는다. 선택은 체크박스에만 있다. 판정과 라벨은 `src/lib/select-all.ts` 의 기존
    순수 함수를 쓴다. 두 번째 판정을 만들지 않는다. (ADR-0043 과 같은 모양)
  - **전체 선택으로 들어온 건이 선택에 남아 있으면 `삭제` 를 열지 않는다.** 사유를 적고
    한 줄씩 고르게 한다. `모두 해제` 로 비우면 다시 열린다.
  - **`숨기기` 는 열어 둔다.** 되돌릴 수 있는 작업이고(ADR-0035) 20건을 한 번에 정리하는
    것이 이 버튼을 둔 이유다.
  - 이 잠금은 **화면에만 있는 보조 장치**다. 선택이 어디서 왔는지는 서버가 알 수 없다.
    아래의 "삭제 판정은 서버가 한다" 는 그대로다.
- 확인 단계에 건수와 작업을 적는다. **삭제 쪽에는 "되돌릴 수 없습니다" 를 쓴다.**
  여기서는 그것이 사실이다. (ADR-0034 의 반대 경우)
- **삭제 판정은 서버가 한다.** 화면의 버튼 비활성은 보조다. 목록이 낡은 사이에 상태가 바뀐다.
- 개인정보 파기 작업(ADR-0022)은 그대로다. 삭제는 운영자의 정리이고 파기는 기한이다.

### 목록 좁히기와 총계 (ADR-0049)

- 검색 폼은 고객명·기간에 **상품 · 연락처 · 결제 방식**을 더해 받는다. 상태는 칩이다.
  - **상품 선택지에 비활성 상품도 넣는다.** 끈 상품의 과거 견적을 찾을 길이 없어지면 안 된다.
  - **연락처는 숫자 부분 일치다.** 입력의 하이픈·공백을 떼고 비교한다. 저장은 숫자만이다.
  - 결제 방식 선택지는 `PAYMENT_METHOD_CHOICES` 에서 만든다. 화면이 값을 손으로 적지 않는다.
    **`미선택` 을 둔다.** 고객이 아직 고르지 않은 건이 실무에서 찾는 대상이다.
  - 연락처로 찾는 것도 개인정보 조회다. 고객명과 같이 `QUOTE_SEARCHED` 를 남기고
    **검색어는 남기지 않는다.** (ADR-0015, ADR-0022)
- **총계는 고른 줄의 합이다.** 자리는 총액 칸의 가장 아래(`tfoot`)이고 건수를 함께 적는다.
  아무것도 고르지 않았으면 `0원` 이다. 빈 칸으로 두지 않는다.
- **검색 결과 전체의 합을 두지 않는다.** 건수에 상한이 없어서 무제한 조회나 DB 집계를
  켜는 길이 된다. 좁히는 것은 필터가 하고 더하는 것은 선택이 한다.
- 더하는 식은 `src/lib/quote-sum.ts` 의 순수 함수 하나다. 컴포넌트가 `reduce` 를 적지 않고
  Repository 의 `_sum` 도 만들지 않는다. 총계는 가격 계산이 아니지만 식의 자리는 하나다.

### 목록 CSV 내보내기 (ADR-0050)

- 길은 `GET /api/admin/quotes/export` 하나다. 목록 화면의 `<a download>` 가 **지금
  좁힌 조건을 그대로** 달고 간다. `page` 는 담지 않는다. 파일에 페이지가 없다.
- **조건 파싱은 `src/services/quote/list-query.ts` 하나다.** 목록 페이지와 내보내기
  라우트가 같은 함수를 쓴다. 두 번 적으면 화면에서 좁힌 것과 파일에 담긴 것이
  어긋나고, **어긋나도 아무 에러가 나지 않는다.** 조건 파싱 자체가 보안 경계다.
- **`publicId` 를 파일에 넣지 않는다.** 그 값은 인증 없는 고객 링크의 주소라서(ADR-0013)
  목록 전체가 든 파일이 모든 고객의 견적을 여는 열쇠 묶음이 된다.
- **금액은 포맷하지 않는다.** `1490000` 이고 `1,490,000원` 이 아니다. `formatKRW` 를
  내보내기 경로에서 부르지 않는다. 쉼표와 `원` 이 붙으면 엑셀에서 문자열이 되어
  더해지지 않는다. 화면은 포맷하고 파일은 포맷하지 않는다.
  **연락처에는 하이픈을 넣는다.** 숫자만 넣으면 엑셀이 앞의 0 을 떼어 먹는다.
- CSV 문자열 변환은 `src/lib/csv.ts` 의 순수 함수 하나다. UTF-8 BOM · CRLF · 따옴표
  겹치기를 그 함수가 한다. 라이브러리를 더하지 않고 `.xlsx` 를 만들지 않는다.
- **수식 주입을 막는다.** `=` · `+` · `-` · `@` · 탭 · CR 로 시작하는 값 앞에 `'` 를
  붙인다. 고객명은 고객이 적은 문자열이다. 판정은 **모든 칸**에 건다. 위험한 칸을
  사람이 골라내는 방식은 칸이 하나 늘 때 깨진다.
- **행 수 상한(`EXPORT_LIMIT`)이 있다.** 먼저 건수를 세고 넘으면 행을 읽지 않는다.
  파일을 만들지 않고 건수와 함께 기간을 좁히라는 사유를 돌려준다. ADR-0049 가 전체 합을
  거부한 이유가 무제한 조회였다. 내보내기는 그 조회를 해야 하므로 **상한을 명시한다.**
- `QUOTE_EXPORTED` 를 남긴다. **건수만** 적는다. 검색 조건·고객명·연락처를 담지
  않는다. (ADR-0015, ADR-0022) `QUOTE_SEARCHED` 와 묶지 않고 **겹쳐 남기지도 않는다.**
  한 동작에 로그 둘이 남으면 검색 건수 집계가 거짓이 된다.
  상한을 넘어 거부한 요청은 남기지 않는다. 내보낸 것이 없다.
- 확인 창을 두지 않는다. 내보내기는 되돌릴 수 없지만 **파괴적이지 않다.** 지우는 것이
  아니라 복사하는 것이다. 위험을 막는 수단이 확인 창이 아니라 감사 로그인 경우다.

## 파괴적 작업

- 삭제 대신 비활성화를 기본으로 한다.
- 일괄 변경(여러 옵션 금액 동시 수정 등)은 영향 건수를 먼저 보여주고 확인을 받는다.
- 되돌릴 수 없는 작업에는 확인 단계를 둔다.
