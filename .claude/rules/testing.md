# 테스트 규칙

Vitest. 테스트 파일은 대상 파일 옆에 `*.test.ts`로 둔다.

## 무엇을 반드시 테스트하는가

| 대상 | 필수 | 방식 |
| ---- | ---- | ---- |
| Pricing Service | 필수 | 단위 테스트, DB 없음 |
| 옵션 제약 검증 | 필수 | 단위 테스트 |
| 상태 전이 | 필수 | 단위 테스트 |
| Repository | 선택 | 실제 테스트 DB |
| API Route | 권장 | 요청→응답 통합 테스트 |
| UI 컴포넌트 | 선택 | 표시·분기만 |

Pricing Service를 수정하는 커밋은 테스트 추가·갱신을 포함한다. 예외 없다.

## 계산 테스트

- 입력과 기대 금액을 **표로 나열**한다. 기대값은 리터럴로 쓴다.
- 기대값을 계산식으로 쓰지 않는다. `expect(total).toBe(96_240)` 이지 `expect(total).toBe(subtotal * 0.95)` 이 아니다.
  구현과 같은 식을 쓰면 버그를 같이 복제한다.
- `docs/pricing-rules.md` 9절의 예시는 회귀 테스트로 고정한다.

반드시 포함할 경계값

- 선택 없음 → 소계 0, 할인 0, 총액 0, 위반 없음 (계산 거부가 아님)
- 할인 조건 직전 (조건 옵션 중 1개 누락) / 조건 충족 / 조건 옵션 + 추가 옵션
- 조건 목록이 빈 할인은 항상 적용 대상인지
- 할인액이 소계를 넘는 경우
- 10원 단위 버림이 실제로 발생하는 금액 (예: 할인액 5,065 → 5,060)
- 버림으로 할인액이 0원이 되는 저액 거래 (ADR-0007)
- 할인 후보가 2개 이상일 때 큰 쪽이 선택되는지, 동률일 때 `priority`로 결정되는지 (ADR-0006)
- 단일 선택 그룹에 2개 선택 → 계산 거부
- 미등록 옵션 식별자 → 계산 거부
- 총액이 항상 10원 단위인지

## 작성 방식

- Pricing Service 테스트는 DB를 띄우지 않는다. 가격 규칙을 픽스처 객체로 넘긴다.
- 시각은 인자로 고정값을 넘긴다. `new Date()`를 테스트에 쓰지 않는다.
- Prisma를 모킹해서 계산 테스트를 하지 않는다. 계산 함수가 순수 함수라 모킹이 필요 없어야 한다.
  모킹이 필요하다면 함수 설계가 잘못된 것이다.
- Repository 테스트는 실제 테스트 DB를 쓴다. 쿼리 결과를 모킹하면 스키마 변경을 잡지 못한다.
- 테스트 간 상태를 공유하지 않는다. 각 테스트는 단독 실행 가능해야 한다.

## 테스트 이름

한 줄로 조건과 기대를 쓴다. 한국어로 써도 된다.

```
조건 옵션을 전부 선택하면 할인이 적용된다
조건 옵션 중 하나라도 빠지면 할인 후보에서 제외된다
할인액이 소계보다 크면 소계까지만 차감한다
아무것도 선택하지 않으면 위반 없이 총액 0원을 반환한다
```

## 금지

- 기대값을 실행 결과로 맞추기(스냅샷 갱신으로 금액 변경을 통과시키기).
- 실패하는 테스트를 `skip` 처리하고 넘어가기.
- 금액 비교에 `toBeCloseTo` 사용. 금액은 정수이므로 `toBe`로 정확히 비교한다.
