# 가격 규칙 추가·변경 절차

금액 계산 결과가 달라지는 변경은 순서를 지킨다. 코드부터 쓰지 않는다.

## 1. 업무 규칙 확정

- `docs/pricing-rules.md`에서 해당 규칙이 적용되는 **계산 순서상의 위치**를 먼저 정한다.
- 기존 규칙과 상호작용을 확인한다: 10원 버림 지점 이전인가 이후인가, 할인 기준 소계에 포함되는가, 할인 후보 비교에 영향을 주는가.
- 입력 금액은 **부가세 포함 금액**이다. 세전 금액을 전제한 규칙을 만들지 않는다. (ADR-0005)
- 문서에 없는 규칙이면 **문서를 먼저 수정**한다. 확정되지 않았으면 `(확인 필요)`로 표시하고 사용자에게 질문한다.

## 2. 설계 판단 기록

계산 결과가 달라지는 선택(적용 순서, 중복 허용, 반올림 위치)을 했으면 `docs/decisions/`에 ADR을 추가한다.
`docs/decisions/0000-template.md`를 복사해 번호를 올려 쓴다.

## 3. 스키마

- `prisma/schema.prisma`에 규칙 테이블을 추가·확장한다.
- `effectiveFrom`을 포함한다. 기존 행 `UPDATE`로 값을 바꾸는 구조를 만들지 않는다.
- 금액은 `Int`, 요율은 `Decimal(7,4)`.
- 마이그레이션 파일을 생성한다. `db push`를 쓰지 않는다.

## 4. Repository

- `src/repositories/pricing-rule.ts`에 조회 함수를 추가한다.
- 조회는 `effectiveFrom <= now` 중 최신 버전만 반환한다.
- 여기에 금액 판단 로직을 넣지 않는다.

## 5. 계산 로직

- `src/services/pricing/` 안의 해당 단계 파일에 구현한다. 새 단계면 파일을 추가하고 `calculate.ts`에서 순서에 맞게 호출한다.
- **순수 함수**로 작성한다. DB 조회·`new Date()`를 함수 내부에서 하지 않는다.
- 결과 객체에 이 규칙의 적용 결과와 적용된 규칙 식별자를 포함한다. 총액에만 반영하고 끝내지 않는다.

## 6. 테스트

- 경계값 테스트를 작성한다. 기대값은 리터럴로 쓴다. 구현과 같은 계산식을 쓰지 않는다.
- `docs/pricing-rules.md` 9절 기준 예시의 금액이 바뀌면 문서와 회귀 테스트를 함께 갱신한다.
- 기존 계산 테스트가 깨지면 **기대값을 고치기 전에** 왜 금액이 바뀌었는지 먼저 설명한다. 의도한 변경이 아니면 구현이 틀린 것이다.

## 7. 관리자 화면

- 관리자가 값을 입력해야 하는 규칙이면 `app/admin/`에 입력 화면을 추가한다.
- 저장 전 계산 미리보기를 제공한다. 미리보기는 같은 Pricing Service를 호출한다.
- 변경 이력 기록을 본 작업과 같은 트랜잭션에 넣는다.

## 완료 확인

- [ ] `docs/pricing-rules.md`에 규칙이 서술되어 있다
- [ ] 판단이 필요했다면 ADR이 있다
- [ ] 단가·요율이 코드에 하드코딩되어 있지 않다
- [ ] 경계값 테스트가 있고 통과한다
- [ ] 계산 결과 객체에 적용 근거가 포함된다
- [ ] 관리자가 값을 바꿀 수 있다 (해당되는 경우)
