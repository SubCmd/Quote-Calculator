# 요구사항

> 이 문서는 **무엇을 만드는가**를 정의한다. 가격 계산의 업무 규칙은 `pricing-rules.md`, 시스템 구성은 `architecture.md`를 본다.
> `(확인 필요)` 표시는 아직 확정되지 않은 가정이다. 구현 전에 확정한다.

## 1. 목적

고객이 옵션을 선택하면 즉시 견적 금액을 확인할 수 있게 하고,
관리자가 개발자 도움 없이 가격 규칙을 수정할 수 있게 한다.

대상은 **일반 소비자(B2C)**다. 따라서 제시 금액은 **현금가**이며, 화면에 보이는 금액과
실제 지불 금액이 달라서는 안 된다. **카드 결제는 현금가에 부가세 10%가 더해지므로**,
그 금액은 결제 방식을 고르는 자리에 함께 적는다. (ADR-0039)

해결하려는 문제:

- 담당자가 엑셀로 견적을 계산하면서 단가를 잘못 적용하는 실수가 발생한다.
- 단가가 바뀔 때 과거 견적이 어떤 단가로 계산되었는지 추적할 수 없다.
- 고객이 금액을 알려면 담당자를 거쳐야 한다.

## 2. 사용자

| 역할 | 설명 | 주요 행동 |
| ---- | ---- | ---- |
| 고객(Guest) | 로그인하지 않은 방문자 | 옵션 선택, 금액 확인, 견적 요청 |
| 담당자(Staff) | 영업·견적 담당 | 견적 조회, 견적 확정, 고객에게 발송 |
| 관리자(Admin) | 가격 정책 담당 | 가격 규칙 등록·수정, 이력 조회 |

## 3. 취급 상품

입시 컨설팅 상품 4종이다. 견적 한 건에는 **상품 하나만** 담는다.
**수량 개념이 없다.** 금액은 선택한 옵션의 조합으로만 결정된다. (ADR-0008)

| 상품 | 옵션 그룹 | 선택 방식 | 항목 |
| ---- | ---- | ---- | ---- |
| 1회성 컨설팅 | 분석 항목 | 여러 개 | 내신 성적 분석 (30분) / 모의고사 성적 분석 (30분) / 생활기록부 분석 (1시간) / 내신 + 생활기록부 분석 (60~70분) |
| 과정 컨설팅 | 회차 | 하나 | 3회차 (1회당 60~80분) / 6회차 (1회당 60~80분) |
| | 소통 방식 | 하나 | 카톡 소통 (6개월) / 이메일 소통 (1년) (회차 선택 후 가능) |
| | 수행평가 자료 요청 | 하나 | 5건 / 10건 (회차 선택 후 가능) |
| | 추가 옵션 | 여러 개 | 모의고사 성적 분석 (30분) (회차 선택 후 가능) |
| 고2 올스토리 | 단계 | 여러 개 | 1~6단계 (각 60~80분, 상담 주제는 한 줄 설명에 있다) |
| | 경쟁률 분석 | 여러 개 | 대학교 경쟁률 분석 (파이널콜) (6단계 선택 후 가능) |
| 고3 올스토리 | 단계 | 여러 개 | 1~4단계 (각 60~80분, 고2 올스토리의 3~6단계와 같은 상담. 금액은 4단계만 다르다) |
| | 경쟁률 분석 | 여러 개 | 대학교 경쟁률 분석 (파이널콜) (4단계 선택 후 가능) |

상담 소요 시간은 **옵션 이름 안에** 넣는다. 별도 컬럼을 만들지 않는다.
이름은 견적에 스냅샷으로 남아 인쇄물까지 따라가므로, 그 고객이 본 소요 시간이 그대로 보존된다. (ADR-0026)
소통 방식의 이용 기간(6개월 / 1년)도 같은 이유로 이름에 넣는다.

올스토리 단계의 이름은 **번호와 괄호 한정까지다.** `1단계 (60~80분)`,
`2단계 (60~80분, 첨삭 제외)`. 금액의 한정인 `첨삭 제외` 는 금액과 같은 줄에 있어야 하므로
이름에 남는다. (ADR-0028) **상담 제목은 한 줄 설명(`summary`)으로 내려간다.** (ADR-0031)
그래서 확정 견적서·인쇄물에는 단계 번호와 소요 시간만 남는다. 설명은 스냅샷이 아니기
때문이다. (ADR-0025) 긴 설명은 그대로 **펼치기(`detail`)** 에 들어간다.

고3 올스토리의 1~4단계는 **고2 올스토리의 3~6단계와 같은 상담**이고 문구가 같다.
**단계 번호는 그 상품 안에서 1부터 다시 붙는다.** (ADR-0029) 고3을 사는 고객이 처음 받는
상담에 `3단계` 가 적혀 있으면 목록이 잘린 것으로 읽힌다. 옵션 `code` 도 번호를 따라
고3에서는 `STAGE_1` ~ `STAGE_4` 다. 두 상품은 각자 자기 옵션 행을 갖는다.
이름에 제목이 없으므로 두 상품의 같은 상담은 이름이 아니라 **상품 탭과 한 줄 설명**으로
구별된다. (ADR-0031)

**금액은 같은 상담이어도 상품마다 다를 수 있다.** (ADR-0030) 고3 4단계는 590,000원이고
같은 상담인 고2 6단계는 490,000원이다. 그래서 금액은 공유하지 않고 상품별로 따로 둔다.

**파이널콜은 단계와 다른 그룹**이고 두 상품 모두 490,000원이다. (ADR-0044) 선행 조건이
단계 그룹 전체가 아니라 **그 안의 한 단계**다. 고2는 6단계, 고3은 4단계이고 둘 다
수시 6장 최종 지원전략 상담이다. 지원할 대학을 정하지 않은 고객에게 경쟁률을 분석할
대상이 없다. 그룹이 다르므로 `모두 선택` 버튼(ADR-0043)에도 들어가지 않는다.

과정 컨설팅의 **추가 옵션**은 회차 중간에 끼워 넣는 상담이다. 다른 선택을 대체하지 않으므로
단일 선택 그룹에 넣지 않고 복수 선택 그룹을 따로 둔다. (ADR-0027)
모의고사 성적 분석은 1회성 컨설팅에도 같은 이름·같은 금액으로 있지만 **별개 옵션**이다.
견적 한 건에는 상품 하나만 담으므로 두 상품이 각자 자기 행을 갖는다.

묶음 할인은 **전단계 할인 1종**이다. **해당 그룹의 항목을 전부 선택했을 때** 자동으로 걸린다. (ADR-0009)

| 할인 | 조건 | 비고 |
| ---- | ---- | ---- |
| 전단계 할인 (고2 올스토리) | 1~6단계 전부 선택 | 정액 45,000원. 총액이 통합등록 금액 1,490,000원이 된다 (ADR-0028) |
| 전단계 할인 (고3 올스토리) | 1~4단계 전부 선택 | 정액 37,000원. 총액이 통합등록 금액 1,150,000원이 된다 (ADR-0030) |

1회성 컨설팅의 **통합 할인은 없다.** 분석 항목을 묶어서 받는 경우는 할인이 아니라
`내신 + 생활기록부 분석` 처럼 **그 자체로 하나의 옵션**이다. (ADR-0026)

묶음 옵션과 그 구성 옵션의 관계는 **데이터로 등록한다.** (ADR-0037)
등록·삭제는 관리자 화면에서 한다. (ADR-0038)

| 묶음 | 구성 | 금액 차이 |
| ---- | ---- | ---- |
| 내신 + 생활기록부 분석 (60~70분) | 내신 성적 분석 + 생활기록부 분석 | 208,000 → 199,000 (9,000원) |

구성 옵션을 전부 고른 고객에게 **더 싼 묶음이 있다고 안내한다.** 금액을 깎지 않고
자동으로 바꾸지도 않는다. 안내는 두 선택이 같은 상담이라고 주장하지 않으므로,
묶음을 고르면 견적서가 한 줄이고 따로 고르면 두 줄이다. 어느 쪽이든 제공 형태와 일치한다.

## 4. 기능 요구사항

### F-1. 견적 계산 (고객)

- F-1-1. 상품을 선택한다. 한 번에 하나만 선택한다.
- F-1-2. 선택한 상품에 해당하는 옵션 그룹과 옵션을 보여준다.
- F-1-3. **전체 선택 보조 체크는 제공하지 않는다.** (ADR-0026) 묶음을 고르는 뜻과 항목을 하나씩
  고르는 뜻이 한 화면에 섞여서, 체크를 켜 둔 고객이 자기가 무엇을 고른 상태인지 읽지 못했다.
  옵션은 전부 같은 방식으로 하나씩 고른다.
  다만 **`모두 선택` 버튼은 둔다.** (ADR-0043) 체크가 아니라 버튼이라 고객의 선택을
  대신 말하지 않고, 저절로 움직이는 **입력**이 없다. 전부 켜져 있지 않으면 전부 켜고,
  전부 켜져 있으면 전부 끈다. 한 번 더 누르면 방금 켠 것이 취소되고 라벨은 `모두 해제` 다.
  라벨은 자기 상태가 아니라 지금 누르면 일어날 일이다.
  어느 그룹에 둘지는 `OptionGroup.selectAll` 이 정한다. 지금은 올스토리 단계 그룹 둘뿐이다.
- F-1-4. 선택이 바뀔 때마다 금액을 다시 계산해 보여준다.
- F-1-5. 금액은 **선택 항목별 금액 → 소계 → 할인 → 총액** 구조로 분해해서 보여준다. 총액에는 `현금가`를 명시한다. (ADR-0039)
  공급가액·세액은 적지 않는다. 카드 결제 금액은 결제 방식을 고르는 자리에만 적는다.
- F-1-6. 금액 계산은 서버에서만 수행한다. 브라우저에서 계산하지 않는다.
- F-1-7. 선택 조합이 유효하지 않으면(단일 선택 그룹에 2개 선택 등) 금액 대신 사유를 보여준다.
- F-1-9. 선행 그룹이 있는 그룹은 선행 선택 전까지 고를 수 없다. (과정 컨설팅의 소통 방식·수행평가 자료·추가 옵션은 회차 선택 후 가능) 선행 선택이 풀리면 딸린 선택도 함께 풀린다. (ADR-0010)
- F-1-8. **아무것도 선택하지 않은 상태의 총액은 0원이다.** 이것은 오류가 아니라 정상 표시다. 계산 결과를 그대로 보여주되, 선택이 없으면 0원이 보인다.
- F-1-10. **묶음 옵션의 구성 옵션을 전부 고르면 더 싼 묶음을 안내한다.** (ADR-0037)
  총액은 고른 그대로이고, 안내가 금액을 깎지 않는다. 바꾸는 것은 고객이 버튼을 눌렀을 때뿐이다.
  절약액이 양수가 아니거나 바꾼 선택이 제약을 위반하면 안내하지 않는다.

### F-2. 견적 저장·요청 (고객)

- F-2-1. 계산 결과를 견적으로 저장할 수 있다.
- F-2-2. 저장 시 연락처 정보를 함께 받는다. 이름·휴대전화 필수, 이메일 선택. (ADR-0013)
- F-2-3. 저장된 견적에는 조회용 식별자가 발급되며, 고객은 그 링크로 다시 볼 수 있다.
- F-2-4. 저장된 견적은 **계산 당시 가격 규칙 스냅샷**을 포함한다. 이후 단가가 바뀌어도 금액이 변하지 않는다.
- F-2-5. 견적에는 유효기간이 있다. 계산 시점 + 30일. (ADR-0012)
- F-2-6. 연락처를 받기 전에 **개인정보 수집·이용 동의**를 받는다. **구현됨 (ADR-0018).**
  목적·수집 항목·보유기간·동의 거부 권리를 고지하고 `[필수]` 체크박스로 동의받는다.
  동의하지 않은 요청은 서버가 거부하고, 동의 시각을 견적에 함께 저장한다.
- F-2-9. **취소·환불 규정 동의를 따로 받는다.** **구현됨 (ADR-0042).** 개인정보 동의와
  근거 법이 달라 체크박스와 저장 컬럼(`refundPolicyConsentAt`)을 나눈다. 둘 다 필수이고,
  하나라도 없으면 서버가 거부한다. 요청 폼에는 요약만 두고 전문은 `/privacy` · `/refund`
  전용 페이지에 둔다. 전문 링크는 새 탭으로 연다. 선택이 클라이언트 상태라 같은 탭에서
  이동하면 고른 것이 사라진다.
- F-2-7. 견적 조회 화면과 견적서에 **입금 계좌**(예금주·은행명·계좌번호)를 표기한다. **구현됨 (ADR-0019).**
  만료·취소된 견적에는 표기하지 않는다.
- F-2-8. 결제 방식을 고르는 자리에 **방식별 지불 금액**을 적는다. (ADR-0033, ADR-0039)
  입금·상담은 현금가 그대로이고, 카드는 현금가 + 부가세 10%(10원 단위 버림)다.
  요약·견적서의 큰 숫자는 현금가 하나다.
- F-2-10. **플랜 주소를 보관하지 못한 고객이 이름과 휴대전화번호로 자기 플랜을 찾는다.**
  **구현됨 (ADR-0045).** `/q/lookup` 이고 인증이 없는 공개 경로다. 문자·이메일 발송 수단이
  없어 링크를 다시 보내 줄 수 없으므로, 고객이 이미 입력한 것으로 다시 찾게 한다.
  - 두 칸을 **모두** 정확히 맞혀야 한다. 이름은 완전 일치, 번호는 숫자만 남겨 완전 일치다.
    부분 일치·유사 검색을 하지 않는다. 관리자 목록의 이름 검색(ADR-0015)과 다른 질의다.
  - 요청은 `POST` 다. 이름·번호도 결과도 URL 에 담지 않는다. 방문 기록·접근 로그·`Referer`
    에 남기지 않기 위해서다. 공유할 수 있는 주소는 개별 플랜의 `/q/{publicId}` 하나다.
  - 결과에는 플랜 번호·상품명·총액(현금가)·상태·요청 날짜만 담는다. 입력한 이름·번호를
    되돌려 적지 않고, 고른 옵션·할인 내역·관리자 메모도 담지 않는다. 자세한 내역은 링크로 간다.
  - 숨긴 플랜(ADR-0035)은 나오지 않는다. 파기된 플랜(ADR-0022)은 연락처가 비어 자연히 빠진다.
  - **못 찾은 이유를 나누어 알려주지 않는다.** 어느 칸이 맞았는지 알려주는 셈이 된다.
  - 같은 IP 10분 10회 **실패**에 닿으면 `429` 다. 성공은 세지 않고, 잠긴 동안의 시도는
    기록하지 않는다. 남은 시도 횟수는 알려주지 않는다. (ADR-0020 과 같은 선)
    **전체 한도는 두지 않는다.** 전체로 잠기면 그 시간 동안 모든 고객이 자기 플랜을 못 찾는다.
  - 모든 조회는 `QUOTE_LOOKED_UP` 으로 남긴다. **조회어는 담지 않고 결과 건수만** 적는다.
    0건도 남긴다. 잠겨서 거부한 요청은 남기지 않는다.
  - 조회는 **읽기뿐이다.** 결제 방식 선택·취소 요청은 `/q/{publicId}` 에 그대로 있다. (ADR-0033)

### F-3. 견적 관리 (담당자)

- F-3-1. 견적 목록을 조회·검색한다. (상태, 기간, 고객명)
- F-3-2. 견적 상세에서 선택 내역과 금액 분해를 확인한다.
- F-3-3. 견적 상태를 변경한다: `DRAFT` → `REQUESTED` → `CONFIRMED` / `EXPIRED` / `CANCELED`
- F-3-4. `CONFIRMED` 견적은 금액과 선택 내역을 수정할 수 없다. 수정이 필요하면 복제해서 새 견적을 만든다.
- F-3-5. (확인 필요) 담당자가 금액을 수동 조정할 수 있는가? 가능하다면 조정 한도와 사유 기록이 필요하다.
- F-3-6. **견적 목록을 정리한다.** (ADR-0035, ADR-0041) 각 줄 앞 체크박스로 고른 뒤 하단에서
  `숨기기` 또는 `삭제` 를 누른다. 전체 선택 체크박스는 두지 않는다.
  - 숨기기: 모든 상태에 쓸 수 있다. 목록·검색·고객 링크에서 함께 사라지고, **되돌릴 수 있다.**
    되돌리기는 `숨긴 견적` 목록에서 상세로 들어가 한 건씩 한다.
  - 삭제: `REQUESTED`·`CANCELED` 만. 행을 실제로 지우고 **되돌릴 수 없다.**
    `CONFIRMED` 가 하나라도 섞이면 아무것도 지우지 않고 사유와 함께 거부한다. 확정 건은
    `confirmedAt` 기준 5년 보존 대상이다. (ADR-0022)
  - 둘 다 확인 단계를 거치고 감사 로그를 남긴다. 삭제 로그에는 연락처를 담지 않는다.

### F-4. 가격 규칙 관리 (관리자)

- F-4-1. 상품, 옵션 그룹, 옵션을 등록·수정·비활성화한다.
  **옵션은 등록·수정·비활성화·재활성화가 모두 구현됨 (ADR-0017, ADR-0023).**
  - 등록: **기존 그룹 안에서만** 가능하다. 같은 그룹에 같은 코드가 있으면(꺼진 것이라도) 거부한다.
  - 수정: **이름과 금액만** 바꿀 수 있고, 새 버전 행을 추가하는 방식이다. 옵션 `code` 는 불변이다(ADR-0009).
  - 비활성화: 같은 코드의 모든 버전을 끄고, 그 옵션을 조건으로 쓰는 할인도 함께 끈다.
  - 재활성화: 모든 버전을 켜고, 함께 꺼진 할인 중 **조건 옵션이 전부 활성이 되는 것만** 되살린다.
  **상품·옵션 그룹의 신설·비활성화는 아직 없다.** 그룹 구조(선행 관계·단일 선택)는 화면에서 편집하지 않는다.
- F-4-2. 옵션별 금액을 등록·수정한다.
- F-4-2-1. **고객 화면에 보이는 순서를 바꾼다.** (ADR-0026) 상품 탭 순서, 단계(그룹) 순서,
  단계 안 옵션 순서 셋 다 바꿀 수 있다. 순서는 금액이 아니라 화면 배치이므로 새 버전을 만들지 않고
  덮어쓰고, 과거 견적의 표시 순서에는 영향을 주지 않는다.
- F-4-3. 할인 규칙(조건 옵션 조합, 할인율 또는 할인액)을 등록·수정·비활성화한다. 전단계 할인의 할인율은 코드가 아니라 이 화면에서 정한다.
  비활성화는 조건 옵션을 건드리지 않고 그 할인만 끈다. 되돌릴 때는 새 버전을 등록한다. (ADR-0026)
- F-4-4. 가격 규칙은 **적용 시작일**을 가진다. 수정은 덮어쓰기가 아니라 새 버전 추가다.
- F-4-4-1. **묶음 관계를 등록·삭제한다.** (ADR-0038) 상품 탭 안에서 묶음 옵션과 구성 옵션
  2개 이상을 골라 추가하거나, 기존 관계를 삭제한다. **수정은 없다.** 구성 하나를 바꾸는 것은
  지우고 다시 넣는 것이다. 관계는 금액이 아니므로 적용 시작일도 새 버전도 없다.
  묶음이 더 싼지는 저장 시점에 검증하지 않는다. 안내 여부는 그때그때의 총액 차이가 정한다. (ADR-0037)
- F-4-5. 변경 이력(누가·언제·무엇을·이전값→새값)을 조회할 수 있다.
- F-4-6. 저장 전에 샘플 입력으로 계산 결과를 미리 확인할 수 있다.

### F-5. 출력

- F-5-1. 견적서를 PDF로 내려받는다. **구현됨 (ADR-0016).** `/q/[publicId]/print` 인쇄 전용 페이지에서
  브라우저 인쇄 → PDF 저장으로 받는다. 서버가 PDF 파일을 만들지는 않는다. 로고·도장 이미지는 범위 외.
- F-5-2. 이메일 발송. **보류 (2026-10-07).** 아직 필요하지 않다고 확인됐다. 필요해지면 다시 결정한다.

## 5. 비기능 요구사항

- N-1. 견적 계산 API 응답은 일반 조합에서 300ms 이내.
- N-2. 금액 오차 0. 동일 입력 + 동일 규칙 버전 → 항상 동일 결과(결정적 계산).
- N-3. 가격 규칙 변경과 견적 상태 변경은 모두 감사 로그를 남긴다.
- N-4. 고객 연락처는 개인정보다. 수집 전에 동의를 받고(ADR-0018), 목록 화면에서는 마스킹하며,
  보관 기간은 미확정 1년 / `CONFIRMED` 5년이다. (ADR-0013)
- N-5. 금액 계산 로직은 단위 테스트로 검증한다. 경계값(선택 없음 0원, 할인 조건 직전/충족, 10원 단위 버림)을 반드시 포함한다.

## 6. 범위에서 제외

- 결제 처리
- 재고 관리
- 다국어·다통화 (원화 단일)
- B2B 견적(부가세 별도 표기), 세금계산서 발행
- 고객 회원가입/로그인 (고객은 비로그인, 담당자·관리자만 인증)

## 8. 아직 확정이 필요한 항목

Q-1(취급 상품·옵션 목록)은 3절로 확정됐다. 금액 자체는 Q-9로 남는다.

| # | 항목 | 왜 필요한가 |
| ---- | ---- | ---- |
| Q-9 | 상품 금액 확정 | **해소됨.** 1회성 컨설팅(ADR-0026)·과정 컨설팅(ADR-0027)·고2 올스토리(ADR-0028)·고3 올스토리(ADR-0029, ADR-0030) 전부 확정값이다. **임시값은 남아 있지 않다.** 금액은 DB 값이므로 이후 변경도 코드 수정 없이 된다. 미등록 상품은 `생기부 첨삭` 하나이고 금액이 정해지면 추가 옵션으로 등록한다 |
| Q-2 | 담당자 수동 금액 조정 허용 여부 | 데이터 모델에 조정 필드가 필요한지 결정된다 |
| Q-3 | 관리자·담당자 인증 방식 | **잠정 결정됨 (ADR-0011).** 공유 비밀번호 하나 + 서명 쿠키로 구현했다. 대입 공격은 **시도 제한으로 막았다 (ADR-0020.** IP별 5회 / 전체 20회, 10분 창**)**. 남은 한계: 감사 로그의 `actor`가 `admin` 고정이라 **누가** 바꿨는지 구분할 수 없고, 공유 비밀번호라 담당자별 추적도 안 된다. 운영 전에 실제 방식을 확정해야 한다 |
| Q-4 | 견적 유효기간 기본값 | **결정됨 (ADR-0012).** 계산 시점 + 30일. `expiresAt` 에 값으로 박고, 만료 여부는 저장하지 않고 조회 시점에 파생한다. `CONFIRMED` 는 만료되지 않는다 |
| Q-5 | 고객 연락처 필수 입력 항목과 보관 기간 | **결정됨 (ADR-0013).** 요청자 이름·휴대폰 필수, 이메일 선택. 학생 정보는 수집하지 않는다. 보관은 미확정 1년 / `CONFIRMED` 5년, 만료 시 개인정보 컬럼만 `NULL` 로 비운다. 동의 절차와 고지 문구는 **ADR-0018 로 확정·구현됨**(고지 보유기간을 1년 / 확정 5년으로 일치시켰다). **파기 배치는 여전히 운영 배포 전 과제** |
| Q-6 | 견적서 PDF 서식과 필수 표기 항목 | **결정됨 (ADR-0016).** 발행처·견적번호·발행일·유효기간·항목별 금액→소계→할인→총액. **공급가액·세액 병기는 ADR-0039 로 없앴다.** 발행처는 `QUOTE_SUPPLIER_*` 환경변수에서 읽고 설정된 항목만 찍는다. 고객 연락처는 넣지 않는다. **법적 필수 문구가 따로 있으면 추가 결정 필요** |
| Q-7 | 결제 연동 필요 여부 | 현재는 범위 외다. 입금은 **계좌 이체 안내**로 갈음한다 (ADR-0019). 가상계좌·PG 연동·입금 자동 대조는 만들지 않았다 |
| Q-8 | 할인 조건을 옵션 버전에 어떻게 묶을지 | **해소됨 (ADR-0009).** 조건은 `(groupCode, optionCode)` 코드 쌍으로 저장하고 Repository가 유효 버전의 행 id로 해석한다. 관리자 화면에서 새 버전을 INSERT 해도 조건이 깨지지 않는 것을 확인했다 |
