# ADR-0022. 개인정보 파기는 CLI 배치가 연락처 컬럼만 비우고, 검색어는 처음부터 남기지 않는다

- 상태: 수락됨
- 날짜: 2026-10-08
- 관련: ADR-0012, ADR-0013, ADR-0015, ADR-0018, `.claude/rules/admin.md`

## 배경

ADR-0013 은 보관 기간을 정해 놓고 **실행 수단은 만들지 않았다.** "운영 데이터가 쌓이기 전에는
돌 일이 없고, 돌지 않는 배치는 썩는다"는 이유였다. 그 판단은 그때는 맞았다. 지금은 실제 고객의
이름·휴대폰을 받기 직전이고, 기간이 지나도 지울 방법이 없는 상태로 공개하면 **첫날부터 위반이 쌓인다.**

정해진 정책은 이렇다. (ADR-0013)

| 구분 | 기간 |
| ---- | ---- |
| `DRAFT` / `REQUESTED` / `CANCELED` | 생성 후 1년 |
| `CONFIRMED` | 확정 후 5년 |

구현하려고 보니 **두 가지가 비어 있었다.**

### 1. 확정 시각을 아무도 기록하지 않는다

`CONFIRMED` 는 "확정 후 5년"인데 `Quote` 에 확정 시각이 없다. `updatedAt` 은 아무 변경에나 바뀌어서
기준이 될 수 없다. 감사 로그(`QUOTE_STATUS_CHANGED`)에는 남지만, 그걸 거꾸로 훑어 기간을 계산하는 것은
**법정 보존기간을 로그 파싱에 맡기는 것**이다.

### 2. 연락처를 비워도 감사 로그에 이름이 남는다

`QUOTE_SEARCHED` 는 고객명 검색을 기록하면서 검색어를 그대로 담는다. (ADR-0015)

```
summary:  고객명 '홍길동' 으로 견적 검색 (3건)
targetId: 홍길동
```

`Quote.customerName` 을 `NULL` 로 만들어도 이 줄은 남는다. 그런데 `.claude/rules/admin.md` 는
**감사 로그를 수정·삭제하지 않는다**고 못박아 뒀다. 파기 의무와 감사 무결성이 정면으로 부딪친다.

## 결정

### 파기는 CLI 배치가 한다

```bash
npm run privacy:purge           # 실제로 지운다
npm run privacy:purge -- --dry  # 대상 건수만 센다
```

- 서버 크론 / 작업 스케줄러가 하루 한 번 부른다. **웹에 노출되는 경로를 만들지 않는다.**
- 관리자 화면 버튼으로 두지 않는다. 법적 의무를 **사람의 기억에 맡기지 않는다.**
- `prisma/seed.ts` 와 같은 `tsx` 방식이라 새 의존성이 없다.
- 기본 동작은 멱등이다. 이미 비운 행은 다시 세지도, 다시 기록하지도 않는다.

### `Quote.confirmedAt` 을 추가한다

- `CONFIRMED` 로 전이할 때 상태 변경과 **같은 트랜잭션에서** 찍는다.
- 기존 `CONFIRMED` 행은 마이그레이션에서 감사 로그의 전이 시각으로 백필하고,
  그마저 없으면 `updatedAt` 으로 채운다.
- `CONFIRMED` 가 아닌 행은 `NULL` 이다. 되돌아오는 전이가 없으므로(ADR-0012) 지울 일이 없다.

### 비우는 것과 남기는 것

| 컬럼 | 파기 | 이유 |
| ---- | ---- | ---- |
| `customerName` · `customerPhone` · `customerEmail` | `NULL` | 사람을 특정하는 값 |
| `privacyConsentAt` | **남긴다** | 동의받았다는 증거다 (ADR-0018) |
| `confirmedAt` · 금액 · 선택 내역 · `snapshot` | **남긴다** | 통계. 사람을 특정하지 않는다 |

행은 지우지 않는다. (ADR-0013)

### 검색어는 처음부터 남기지 않는다

- `logQuoteSearch` 가 **검색어를 더 이상 저장하지 않는다.** 결과 건수만 남긴다.
- 이미 쌓인 `QUOTE_SEARCHED` 행은 1년이 지나면 배치가 이름을 가린다.

## 이유

- **CLI 를 고른 이유.** 배포처가 아직 안 정해졌다. API Route 로 만들면 크론 시크릿 인증 방식을
  지금 추측해야 하고, **인증이 약한 공개 경로 하나가 늘어난다.** CLI 는 서버에 들어올 수 있는
  사람만 돌릴 수 있다. 배포처가 정해지면 그때 같은 Service 를 부르는 Route 를 얹으면 된다.
- **버튼으로 두지 않은 이유.** 파기는 담당자가 원할 때 하는 일이 아니라 기한이 지나면 해야 하는 일이다.
  아무도 안 누르면 아무 일도 안 일어나는 설계는 의무를 지키는 설계가 아니다.
- **`confirmedAt` 을 컬럼으로 둔 이유.** 보존기간의 기준점은 **데이터여야 한다.** 로그에서 유도하면
  로그 형식이 바뀌는 순간 기간 계산이 조용히 틀어지고, 틀어진 것을 알아챌 방법이 없다.
- **`privacyConsentAt` 을 남기는 이유.** 동의 시각을 지우면 "동의받고 처리했다"를 증명할 수 없다.
  시각 자체는 누구인지 알려주지 않는다. ADR-0018 이 이미 파기 대상이 아니라고 적어 뒀다.
- **검색어를 안 남기기로 한 이유.** 감사 로그의 목적은 **"담당자가 이름으로 훑어봤다"는 사실**을
  남기는 것이지(ADR-0015) 그 이름을 보관하는 것이 아니다. 누가·언제·몇 건 맞았는지만 있어도
  그 목적은 달성된다. 저장하지 않으면 파기할 것도 없다. ADR-0013 의 "수집하지 않은 정보는
  유출될 수 없다"와 같은 손익이다.
- **그래도 기존 행을 가리는 이유.** 이미 저장된 이름은 "안 남긴다"로 사라지지 않는다.
  감사 로그 불변 규칙의 예외지만, **법정 파기 의무가 내부 운영 규칙보다 위에 있다.**
  가리는 것도 파기 기록으로 남기므로 무엇이 일어났는지는 추적된다.
- **삭제가 아니라 비우기인 이유는 ADR-0013 과 같다.** 견적 건수·금액 통계가 과거로 소급해 바뀌지 않는다.

## 하지 않기로 한 것

- **파기 예고 알림.** 고객에게 "곧 지웁니다"라고 보낼 수단이 없다. 이메일은 선택값이고
  발송 기능 자체가 아직 없다(F-5-2). 보낼 수 없는 알림을 설계하지 않는다.
- **파기 취소·복구.** 파기는 되돌릴 수 없어야 의미가 있다. 복구 경로를 두면 파기가 아니다.
- **`QuoteItem` 손대기.** 선택한 옵션과 금액뿐이라 사람을 특정하지 않는다.
- **`publicId` 무효화.** 파기된 견적의 주소를 열면 연락처가 빈 견적이 보인다.
  금액은 남기기로 한 이상 주소를 막을 이유가 없고, 막으려면 `notFound()` 와 구분이 안 된다.
- **감사 로그 행 삭제.** 가리는 것까지만 한다. 행을 지우면 파기했다는 사실도 같이 사라진다.
- **스케줄러 설치.** 배포처가 정해져야 크론이든 작업 스케줄러든 고를 수 있다.
  README 의 운영 공개 전 항목으로 남긴다.

## 영향

- `QUOTE_SEARCHED` 의 `targetId` 가 더 이상 고객명이 아니다. 검색어로 감사 로그를 되짚는
  조회는 불가능해진다. **그게 의도다.**
- 파기된 견적은 관리자 목록·상세에서 연락처가 빈 칸으로 보인다. 마스킹과 다르게 복구할 값이 없다.
- 배치가 돌지 않으면 아무 일도 일어나지 않는다. **스케줄러에 등록하는 것까지가 이 작업의 완료다.**
  등록 전에는 README 가 미완료로 표시한다.
- 보유기간을 바꾸려면 `src/services/privacy/retention.ts` 의 상수와 **ADR-0018 의 고지 문구**를
  함께 고쳐야 한다. 둘 중 하나만 고치면 고지가 거짓이 된다.
