# ADR-0032. 표시 순서는 위아래 버튼이 아니라 자리 번호 입력으로 바꾼다

- 상태: 수락됨
- 날짜: 2026-10-13
- 관련: ADR-0023, ADR-0026

## 배경

ADR-0026 은 순서 변경 요청을 **전체 순열**로 받기로 했다. 화면은 그 순열을 만드는
수단으로 `↑` `↓` 버튼을 두었다. 한 칸씩 교환하고 저장할 때 전체를 보냈다.

올스토리 단계가 여섯 개가 되면서 이 방식의 비용이 드러났다. 맨 아래를 맨 위로 올리려면
다섯 번 눌러야 하고, 누르는 동안 줄이 매번 움직인다. 관리자가 원하는 것은 "이 항목을
한 칸 위로" 가 아니라 "순서를 1, 2, 3, 4, 5, 6 으로 이렇게" 다.

## 결정

### 1. 각 줄에 자리 번호를 입력한다

```
[ 1 ]  1단계 (60~80분)
[ 2 ]  2단계 (60~80분, 첨삭 제외)
[ 3 ]  3단계 (60~80분)
```

`number` 입력에 현재 자리가 들어 있고, 관리자가 고친다. 서버로 가는 것은 번호가 아니라
**키 순열** 그대로다. API 는 바뀌지 않는다. (ADR-0026)

### 2. 1 ~ N 이 빠짐없이 한 번씩이어야 저장할 수 있다

- 빈칸·정수 아님·범위 밖 → `번호는 1부터 N 사이의 정수로 넣으세요.`
- 중복 → `번호가 겹칩니다. 겹친 번호 2, 빠진 번호 4.`
- 유효하지 않으면 저장 버튼이 열리지 않는다. 번호를 추측해 채우지 않는다.

판정은 `src/lib/order-input.ts` 의 순수 함수 하나다. 화면이 조건문을 직접 들고 있지 않다.
(ADR-0023 의 `option-revival` 과 같은 방식)

### 3. 번호를 고쳐도 줄은 제자리에 있고, 결과는 미리보기로 보여준다

유효한 순열이고 현재 순서와 다를 때만 아래에 새 순서를 번호 목록으로 띄운다.

## 이유

### 왜 번호 입력인가

버튼은 **연산**이고 번호는 **상태**다. 관리자의 머릿속에 있는 것은 최종 배치이지
거기까지 가는 교환 횟수가 아니다. 여섯 줄을 원하는 순서로 바꾸는 데 버튼은 최악의 경우
교환 열다섯 번이 필요하고, 번호는 고칠 줄만큼만 손댄다.

버튼은 **되돌리기가 어렵다.** 네 번 누른 뒤 "원래 어디였지" 가 화면에 남아 있지 않다.
번호는 틀린 칸만 다시 적으면 되고, `되돌리기` 가 전부를 처음 번호로 복구한다.

### 왜 너그럽게 처리하지 않는가

번호를 일부만 적게 하고 나머지를 뒤에 붙이는 방식이 편해 보인다. 그러면 적지 않은 줄의
자리를 화면이 정하게 되고, 관리자가 보지 않은 순서가 저장된다. ADR-0026 이 서버에서
부분 목록을 거부한 이유(`보내지 않은 항목의 자리를 서버가 추측하는 셈`)가 화면에도 그대로
적용된다.

겹친 번호를 "나중에 적은 쪽이 이긴다" 로 푸는 것도 같은 문제다. 두 줄에 `1` 이 있을 때
어느 쪽이 1번인지는 관리자가 정해야 한다.

### 왜 중복과 누락을 함께 알려주는가

번호가 전부 1 ~ N 안에 있고 줄 수가 N 이면 중복과 누락은 **항상 함께 생긴다.** 겹친
번호만 알려주면 어느 번호가 비었는지 관리자가 세어 봐야 한다. 둘 다 적으면 고칠 칸이 바로 보인다.

### 왜 줄을 움직이지 않는가

번호를 고치는 즉시 줄이 재배치되면, 방금 누른 입력 칸이 커서 아래에서 사라진다. 여섯 줄을
연달아 고치는 동안 어디를 고치던 중인지 놓친다. 입력 칸이 움직이지 않으면 위에서 아래로
한 번 훑으며 번호를 적을 수 있다.

대신 결과를 볼 수 없으면 저장이 도박이 된다. 그래서 미리보기를 둔다. 유효하지 않은
동안에는 보여줄 순서가 없으므로 사유만 띄운다.

### 왜 `.order-number` 너비를 고정하는가

줄마다 입력 칸 너비가 다르면 제목이 시작하는 위치가 어긋나서 목록을 세로로 훑을 수 없다.
순서를 바꾸는 화면에서 세로 훑기는 하려는 일 자체다.

## 하지 않기로 한 것

- **드래그 앤 드롭.** 포인터 전용이라 키보드로 순서를 바꿀 수 없고, 라이브러리가 들어온다.
  번호 입력은 `number` 하나로 끝나고 탭 이동만으로 전부 조작된다.
- **`↑` `↓` 버튼 병행.** 같은 일을 하는 수단이 둘이면 둘 다 유지해야 하고, 버튼이 번호를
  고치는 중간 상태를 건드리면 둘 중 무엇이 참인지 모호해진다.
- **번호를 고치는 즉시 줄 재배치.** 위 이유.
- **빈 칸 허용 후 자동 채우기.** 관리자가 적지 않은 순서가 저장된다.
- **단건 "위로" API.** ADR-0026 그대로다. 번호 입력도 저장은 전체 순열이다.
- **번호 입력 검증을 서버에 추가하기.** 서버가 받는 것은 키 순열이고 `planReorder` 가
  이미 전부 검증한다. 번호는 화면 안에서만 존재한다.

## 영향

- `app/admin/pricing-admin.tsx` 의 `OrderList` 가 번호 입력으로 바뀐다. 세 호출처
  (상품 탭·단계·옵션)는 `onSave(keys)` 를 그대로 받으므로 고치지 않는다.
- `src/lib/order-input.ts` 와 테스트가 새로 생긴다.
- `app/globals.css` 의 `.order-list` 에서 CSS 카운터가 사라진다. 번호는 입력 칸이 보여준다.
  `.order-buttons` 가 사라지고 `.order-number`·`.order-preview` 가 생긴다.
- API·Service·Repository·스키마 변경 없다.
