# ADR-0024. 요청자 IP 는 `CF-Connecting-IP` 만 믿고, 없으면 한 칸으로 모은다

- 상태: 수락됨
- 날짜: 2026-10-08
- 관련: ADR-0020, ADR-0011, `.claude/rules/admin.md`, `src/lib/client-ip.ts`

## 배경

ADR-0020 은 로그인 시도를 IP별 5회 / 전체 20회로 제한했다. 그때는 배포 경로를 몰라서
`x-forwarded-for` 의 **맨 왼쪽** 값을 IP 로 썼고, "신뢰할 수 있는 프록시 뒤라고 전제할 수 없다"고
적은 뒤 전체 상한을 안전망으로 두는 선택을 했다.

그 전제가 바뀌었다. 이 서비스는 **Cloudflare Tunnel 뒤에서만** 공개된다
(`didaro.net` → Cloudflare → `cloudflared` → `localhost:3100`). 즉 인터넷에서 오는 요청은
예외 없이 Cloudflare 를 거친다.

그런데 `x-forwarded-for` 를 쓰는 동안은 프록시가 생겨도 안전해지지 않는다.
**Cloudflare 는 이 헤더를 덮어쓰지 않고 클라이언트가 보낸 값 뒤에 덧붙인다.**
공격자가 `X-Forwarded-For: 1.2.3.4` 를 붙여 보내면 맨 왼쪽은 `1.2.3.4` 가 된다.
요청마다 값을 바꾸면 IP별 5회 제한은 매번 빈 칸에서 시작하므로 **사실상 없는 것과 같다.**
남는 것은 전체 20회뿐인데, 그건 정상 관리자까지 10분 막는 거친 그물이다.

`CF-Connecting-IP` 는 다르다. Cloudflare 가 자기가 본 TCP 접속 주소로 **항상 덮어쓴다.**
클라이언트가 같은 이름으로 보내도 교체된다.

## 결정

**`CF-Connecting-IP` 하나만 읽는다. 없으면 `"unknown"` 으로 본다.**

- `x-forwarded-for` 와 `x-real-ip` 는 **읽지 않는다.** 대체 수단으로도 쓰지 않는다.
- 헤더가 없는 요청은 전부 `"unknown"` 한 칸에 모인다. 그 칸도 IP별 한도(5회)를 그대로 받는다.
- 전체 20회 상한은 ADR-0020 그대로 둔다.

## 이유

- **"덮어쓰는 헤더"와 "덧붙이는 헤더"는 신뢰도가 다르다.** 프록시 뒤에 있다는 사실만으로는
  부족하고, 그 프록시가 해당 헤더를 **교체**해야 믿을 수 있다. Cloudflare 가 교체하는 것은
  `CF-Connecting-IP` 다. 그러니 그것만 읽는다.
- **없을 때 다른 헤더로 흘러내리지 않는 이유.** 흘러내리면 공격자는 `CF-Connecting-IP` 를 빼고
  `x-forwarded-for` 를 위조해 보내는 것만으로 옛날 구멍을 되살릴 수 있다.
  대체 경로가 있는 한 제한은 가장 약한 경로의 강도를 갖는다.
- **`"unknown"` 한 칸에 모으는 것이 안전한 쪽이다.** Cloudflare 를 거치지 않은 요청은
  (a) 로컬 개발이거나 (b) 이 PC 에서 `localhost:3100` 을 직접 때리는 경우다.
  (b) 를 할 수 있는 상대는 이미 PC 에 들어와 있어서 로그인 제한으로 막을 대상이 아니다.
  그래서 이 칸을 느슨하게 둘 이유가 없고, 한 칸에 모아 5회로 잠그는 편이 낫다.
- **개발이 불편해지지 않는다.** 로컬에서 비밀번호를 5번 틀리면 10분 잠기는데,
  이는 `AdminLoginAttempt` 행을 지우면 즉시 풀린다. 혼자 쓰는 환경이라 충돌이 없다.

## 하지 않기로 한 것

- **Cloudflare IP 대역을 검증해서 `x-forwarded-for` 를 조건부로 믿기.** 대역 목록을 주기적으로
  갱신해야 하고, 갱신이 밀리면 정상 요청을 틀린 IP 로 집계한다. 교체되는 헤더가 이미 있는데
  관리 비용이 드는 우회로를 만들 이유가 없다.
- **`CF-Connecting-IP` 가 없는 요청을 거부(`400`)하기.** 로컬 개발과 헬스 체크가 같이 막힌다.
  IP 판정 함수가 요청의 수락 여부를 정하는 것은 역할을 넘는 일이다.
- **`unknown` 을 IP별 한도에서 제외하기.** 제외하면 헤더를 아예 안 보내는 것이
  제한을 피하는 가장 쉬운 방법이 된다.

## 영향

- `src/lib/client-ip.ts` 는 **Cloudflare 뒤라는 배포 전제에 묶인다.** 배포 경로를 바꾸면
  (Vercel 로 옮기거나 터널을 걷어내면) 이 파일을 **먼저** 고쳐야 한다. 그대로 두면 모든 요청이
  `"unknown"` 한 칸에 모여 IP별 한도가 전체 5회처럼 작동하고, 관리자가 쉽게 잠긴다.
- ADR-0020 의 "프록시 뒤라고 전제할 수 없다"는 서술은 이 ADR 로 갱신된다.
  전체 상한을 둔 판단 자체는 유지된다. 위조 방어가 아니라 **분산 시도 방어**로서 여전히 필요하다.
- `AdminLoginAttempt.ip` 컬럼 주석의 "위조될 수 있다"는 설명은 `"unknown"` 칸에만 해당하게 된다.
