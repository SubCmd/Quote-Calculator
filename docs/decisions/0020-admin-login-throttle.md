# ADR-0020. 관리자 로그인은 IP별 5회 + 전체 20회로 막고, 마지막 실패 10분 후 풀린다

- 상태: 수락됨 (IP 출처는 ADR-0024 로 대체)
- 날짜: 2026-10-08
- 관련: ADR-0011, ADR-0013, ADR-0024, Q-3, `.claude/rules/admin.md`

> 아래 "왜 IP 만으로는 부족한가" 의 전제(배포 경로를 몰라 프록시 뒤라고 볼 수 없다)는 더 이상
> 사실이 아니다. 서비스는 Cloudflare Tunnel 뒤에서만 공개된다. IP 출처는 **ADR-0024** 를 따른다.
> 한도·창·전체 상한 등 이 ADR 의 나머지 결정은 그대로 유효하다.

## 배경

관리자 인증은 공유 비밀번호 **하나**다. (ADR-0011) 비밀번호를 맞히면 가격 규칙 전체와
모든 고객의 이름·휴대전화번호가 열린다. (ADR-0013) 그런데 지금은 시도 횟수 제한이 없어서
`POST /api/admin/login` 을 초당 수십 번 때려도 아무 일이 없다.

계정이 여러 개면 공격자가 아이디도 맞혀야 하지만, 여기는 맞힐 것이 비밀번호 하나다.
`ADMIN_PASSWORD` 가 짧거나 사전에 있는 단어면 온라인 대입으로 뚫린다.
Q-3(실제 인증 방식 확정)은 아직 미정이고, 그때까지 이 구멍을 열어 둘 수는 없다.

### 왜 IP 만으로는 부족한가

Next.js 15 의 Route Handler 는 소켓의 원격 주소를 주지 않는다. `NextRequest.ip` 는 없어졌고,
얻을 수 있는 것은 `x-forwarded-for` / `x-real-ip` **헤더**뿐이다. 헤더는 클라이언트가 보낸 값이다.

신뢰할 수 있는 프록시(Vercel·Cloudflare·nginx)가 이 헤더를 덮어써 주면 맨 왼쪽 값이 실제 클라이언트다.
그런 프록시 뒤가 아니면 공격자가 요청마다 `x-forwarded-for` 를 바꿔서 IP별 제한을 그냥 통과한다.
이 저장소에는 배포 설정(`vercel.json`·Dockerfile 등)이 없어서 **프록시 뒤라고 전제할 수 없다.**

## 결정

**실패한 로그인 시도를 DB 에 남기고, IP별·전체 두 기준으로 잠근다.**

| 기준 | 한도 | 창 | 잠금 |
| ---- | ---- | ---- | ---- |
| 같은 IP | 5회 | 10분 | 그 IP 만 |
| 전체 | 20회 | 10분 | 전부 |

- 창 안의 실패 횟수가 한도에 닿으면 비밀번호를 **보지도 않고** `429` 를 돌려준다.
- 잠금은 **마지막 실패로부터 10분** 후에 풀린다. 응답에 `Retry-After` 와 남은 분을 함께 넣는다.
- **잠겨 있는 동안의 시도는 기록하지 않는다.** 아래 "이유" 참조.
- 로그인에 **성공하면 그 IP 의 실패 기록만 지운다.** 전체 누적은 건드리지 않는다.
- 판정은 순수 함수 `evaluateLoginLock(ip, global, now)` 한 곳에서 한다. 한도·창은 그 파일의 상수다.

## 이유

- **전체 상한이 IP 위조를 막는 안전망이다.** IP별 제한만 두면 헤더를 바꿔 가며 무한히 시도할 수 있다.
  전체 상한은 헤더와 무관하게 세므로 위조해도 20회에서 멈춘다.
  IP별 제한은 프록시 뒤일 때 "정상 관리자는 안 잠기고 공격자만 잠기는" 정밀도를 준다. 둘은 역할이 다르다.
- **전체 잠금이 관리자를 10분 막는 것을 받아들인다.** 공격자가 전체 상한을 계속 때리면
  정상 관리자도 그동안 못 들어온다. 그래도 **고객 연락처 전체가 열리는 쪽이 훨씬 비싸다.**
  관리자는 10분 뒤에 들어오면 되고, 고객 개인정보는 한 번 새면 되돌릴 수 없다.
- **잠긴 동안의 시도를 기록하지 않는 이유는 영구 잠금을 피하기 위해서다.** 기록하면 창이 계속 새로 채워져서
  공격자가 때리는 동안 잠금이 끝나지 않는다. 그건 공격자가 관리자를 영구히 차단할 수 있다는 뜻이다.
  기록하지 않으면 잠금은 마지막 **실제** 실패 10분 후에 반드시 풀린다.
- **성공이 전체 누적을 지우지 않는 이유.** 지운다면 공격자가 (어떻게든) 한 번 성공할 때마다
  시도 예산이 초기화된다. 반대로 IP별 기록은 지운다. 비밀번호를 두 번 틀리고 세 번째에 맞힌
  정상 관리자가 다음 로그인에서 2회를 이미 쓴 상태로 시작하면 안 된다.
- **DB 에 두는 이유는 프로세스가 여러 개일 수 있기 때문이다.** 메모리 `Map` 에 담으면
  인스턴스가 2개면 한도가 2배가 되고, 재배포하면 초기화된다. 제한이 "대충" 걸리는 것은 제한이 아니다.
  PostgreSQL 은 이미 쓰고 있어서 새로 끌어올 의존성이 없다. Redis 를 넣을 이유가 없다.
- **비밀번호 검증보다 잠금 검사를 먼저 하는 이유.** 잠긴 요청에 대해서는 비밀번호를 비교조차 하지 않는다.
  비교를 하면 틀렸는지 맞았는지에 따라 응답 시간이 갈려서, 잠긴 상태에서도 맞는 비밀번호를
  골라낼 수 있는 실마리가 남는다.
- **`429` 를 쓰는 이유.** `401`(비밀번호 틀림)과 `429`(너무 많이 시도함)는 다른 사실이다.
  화면이 "비밀번호가 틀렸다"고 말하면 관리자는 맞는 비밀번호를 계속 다시 넣는다.

## 하지 않기로 한 것

- **남은 시도 횟수를 응답에 알려주기.** "2회 남았습니다"는 공격자에게 한도를 알려주는 것이다.
  정상 관리자에게 필요한 정보는 "지금 잠겼고 몇 분 뒤에 풀린다"뿐이다.
- **CAPTCHA.** 외부 서비스 의존과 개인정보 전송이 따라붙는다. 관리자 한 명이 쓰는 화면에
  그 비용을 낼 이유가 없다. 대입 공격은 횟수 제한으로 충분히 비싸진다.
- **지연(실패마다 sleep)을 주기.** 서버 쪽 요청을 붙잡아 두는 방식이라 그 자체가 자원 소모 공격이 된다.
- **감사 로그(`AuditLog`)에 실패를 남기기.** 공격받는 동안 양이 폭증해서 가격 변경·열람 기록을 묻는다.
  `AuditLog` 는 "누가 무엇을 바꿨나"를 보는 곳이다. 시도 기록은 전용 테이블에 있고 그게 기록이다.
- **IP 영구 차단(블랙리스트).** 차단 목록을 사람이 관리해야 하고, 공유 IP 를 영구히 막는 사고가 난다.
- **비밀번호 해싱·사용자 테이블.** ADR-0011 그대로 Q-3 확정 시점의 일이다.
  시도 제한은 인증 방식이 무엇으로 바뀌어도 그대로 쓰인다.

## 영향

- `AdminLoginAttempt` 테이블이 생긴다. **실패만** 담는다. 성공은 담지 않는다.
  `.claude/rules/database.md` 는 사용자 행위로 생기는 모델에 `createdBy` 를 요구하지만
  이 테이블에는 두지 않는다. 기록 대상이 **인증되지 않은 요청**이라 남길 주체가 없다.
  그 자리를 `ip` 가 대신하고, 위조될 수 있다는 것까지 컬럼 주석에 적는다.
- **창을 벗어난 행은 로그인 시도마다 함께 지운다.** 판정에 쓰이지 않는 데이터다.
  별도 정리 배터리가 필요 없다. ADR-0013 의 개인정보 파기와 달리 보존 의무가 없다.
- 공유 비밀번호를 여러 담당자가 쓰면 서로의 실패가 합산된다. 전체 상한이 그런 구조다.
  담당자별 추적이 필요해지는 시점이 Q-3 확정 시점이다.
- `ADMIN_PASSWORD` 를 **여전히 길고 추측 불가능하게** 둬야 한다. 시도 제한은 대입을 느리게 만들 뿐
  약한 비밀번호를 안전하게 만들지 않는다. 10분에 5회라도 `1234` 는 언젠가 뚫린다.
