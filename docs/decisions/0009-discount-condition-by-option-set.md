# ADR-0009: 할인 조건은 옵션 조합으로 정의한다

- 상태: 승인
- 날짜: 2026-10-06

## 배경

할인 조건은 원래 `minQty`(이 수량 이상이면 적용)였다. 수량이 없어지면서(ADR-0008)
조건을 표현할 방법이 사라졌다.

실제로 필요한 할인은 두 종류이고, 둘 다 **묶음 할인**이다.

- 통합 할인: 1회성 컨설팅의 분석 항목 3개를 모두 선택하면 할인.
- 전단계 할인: 올스토리의 모든 단계를 선택하면 할인. 학년별로 단계 수가 다르다(고2 6단계, 고3 4단계).

## 결정

할인 규칙에 **조건 옵션 목록**을 둔다. 그 옵션을 **전부 선택했을 때** 적용 대상이 된다.

- 조건은 `(옵션 그룹 코드, 옵션 코드)` 쌍의 목록으로 저장한다.
- 조건 목록이 비어 있으면 **항상 적용 대상**이다. (전체 할인 쿠폰)
- "전부 포함"이지 "정확히 일치"가 아니다. 조건 외 옵션을 더 골라도 할인은 유지된다.

조건을 **옵션 행 id가 아니라 코드로** 저장한다.

## 이유

- 조건을 코드가 아니라 데이터로 두면 관리자가 조합을 바꿀 수 있다.
  "통합 할인" "전단계 할인"을 각각 특수 분기로 구현하면 상품이 추가될 때마다 코드를 고쳐야 한다.
- 전단계 할인은 학년마다 단계 수가 다르다. "그룹의 모든 옵션"이라는 암묵 규칙 대신
  명시적 목록으로 두면 관리자가 4번째 분석 항목을 추가해도 기존 할인 조건이 저절로 바뀌지 않는다.
  조건 변경은 항상 의도된 조작이어야 한다.
- 코드로 저장하는 이유는 버전 문제다. 가격 규칙 수정은 `UPDATE`가 아니라 새 행 `INSERT`다(ADR-0002).
  금액만 바꾼 새 옵션 버전을 넣으면 행 id가 바뀐다. 조건이 id를 가리키면
  **가격을 바꾸는 순간 할인 조건이 구 버전을 가리켜 조용히 깨진다.**
  코드는 버전이 바뀌어도 유지되는 식별자다. (`docs/requirements.md` Q-8)

## 대안

**"해당 그룹의 모든 옵션 선택"을 조건 타입으로 둔다.**
현재 두 할인이 정확히 이 형태라서 더 짧게 끝난다.
택하지 않은 이유: 그룹에 옵션을 추가하면 할인 조건이 자동으로 바뀐다.
관리자가 분석 항목을 하나 더 넣었을 때 통합 할인 조건이 말없이 4개로 늘어나는 것은 사고다.

**조건을 표현식(DSL)으로 둔다.** OR·개수 조건까지 표현할 수 있다.
현재 필요한 것은 AND 하나뿐이다. 필요해지면 그때 넓힌다.

## 영향

- `DiscountRule.minQty`를 제거하고 `DiscountCondition` 테이블을 추가한다.
  (`discountRuleId`, `groupCode`, `optionCode`)
- 코드 → 옵션 행 id 해석은 **Repository의 책임**이다.
  Repository는 계산 시점에 유효한 옵션 버전을 이미 알고 있으므로 그 id로 바꿔 Service에 넘긴다.
  `calculate`는 `requiredOptionIds`를 받아 선택 집합에 전부 포함되는지만 본다. 순수 함수로 남는다.
- 해석에 실패한 조건(없는 코드)은 **예외**다. 조용히 조건을 무시하면 할인이 과하게 걸린다.
- 후보가 여러 개면 여전히 할인액 최대 1건만 적용한다. (ADR-0006) 이 결정은 조건 판정만 바꾼다.
- 화면의 `통합` / `전단계` 체크는 조건 옵션을 한 번에 켜는 버튼이다. 할인 자체를 고르는 입력이 아니다.
  할인은 서버 계산 결과로만 나타난다.
