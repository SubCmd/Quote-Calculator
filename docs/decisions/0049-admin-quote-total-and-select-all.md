# ADR-0049. 목록 총계는 가격 계산이 아니고, 전체 선택은 삭제를 겨누지 않는다

- 상태: 수락됨
- 날짜: 2026-10-19
- 관련: ADR-0026, ADR-0032, ADR-0039, ADR-0041, ADR-0043, ADR-0047, `CLAUDE.md`,
  `.claude/rules/admin.md`, `.claude/rules/ui.md`

## 배경

담당자가 묻는 것은 "이번 달 올스토리 입금 건이 얼마인가" 다. 지금 견적 목록은 줄마다
총액을 보여주지만 합을 보여주지 않아서, 계산기를 따로 켜고 스무 줄을 손으로 더한다.
그리고 좁히는 수단이 고객명과 기간뿐이라 상품별·결제 방식별로는 애초에 묶을 수 없다.

합을 보여주려면 두 가지가 걸린다.

**첫째, 금액을 더하는 자리가 없다.** `CLAUDE.md` 절대 규칙 1 은 "금액 계산은 Pricing
Service 안에서만 한다. UI, API Route, Repository, 데이터베이스는 금액을 계산하지 않는다"
다. `.claude/rules/ui.md` 는 "합계를 만들기 위한 `reduce`, `*`, `+` 를 컴포넌트에
쓰지 않는다" 로 더 못 박아 두었고, `.claude/rules/database.md` 는 집계 뷰로 금액을
산출하는 것도 막는다. 글자대로 읽으면 총계를 적을 수 있는 레이어가 하나도 없다.

**둘째, 고르는 수단이 없다.** 고른 줄의 합을 보려면 스무 줄을 스무 번 눌러야 한다.
그런데 ADR-0041 §1 이 **전체 선택 체크박스를 금지했다.** 이유가 분명하다 — 입력 하나가
20건을 고르게 만들면, 지울 생각이 없던 건이 선택에 들어온 것을 읽지 못한다. 같은
체크박스가 `삭제` 버튼을 겨누고 있기 때문이다.

## 결정

### 1. 총계는 **가격 계산이 아니다.** 저장된 금액의 집계다

절대 규칙 1 이 지키려는 것은 **고객이 지불할 금액을 만드는 자리가 하나** 라는 것이다.
옵션 금액·할인율·버림이 여러 곳에 흩어지면 화면과 견적서가 어긋난다. 총계에는 그 셋이
하나도 없다.

| | 가격 계산 | 목록 총계 |
| ---- | ---- | ---- |
| 입력 | 고객의 선택과 가격 규칙 | 이미 저장된 `totalAmount` |
| 하는 일 | 옵션 합 · 할인 비교 · 10원 버림 | 정수 덧셈 |
| 반올림 지점 | 항목 소계, 할인액 | 없다 |
| 틀리면 | 고객이 다른 금액을 낸다 | 담당자가 잘못 집계한다 |

저장된 값은 원 단위 정수 현금가다. (ADR-0001, ADR-0039) 정수를 더하면 정확하고 새
반올림 지점이 생기지 않는다. 그래서 **총계는 Pricing Service 밖에서 만들어도 된다.**

### 2. 더하는 식은 `src/lib/quote-sum.ts` 의 순수 함수 하나다

예외를 열었으니 자리를 못 박는다.

- 컴포넌트가 `reduce` 나 `+` 를 **직접 적지 않는다.** `sumTotals(rows)` 를 부른다.
  ui.md 의 금지는 그대로 살아 있다. 금지된 것은 식을 화면에 적는 것이다.
- `src/lib/` 다. `src/services/` 가 아니다. 선택이 클라이언트 상태라서 그 함수를
  클라이언트 컴포넌트가 쓴다. Service 를 import 하면 Repository 와 `node:crypto` 까지
  번들에 끌려온다. `src/lib/payment-method.ts` 가 같은 이유로 거기 있다.
- Repository 의 `_sum` 도 DB 집계 뷰도 만들지 않는다. database.md 가 막은 것은 그쪽이고,
  이 결정은 거기를 열지 않는다.

### 3. 총계는 **고른 줄의 합**이다. 검색 결과 전체가 아니다

```
요청 일시        상품      고객    연락처           총액       결제 방식  상태
☑ 10/18 14:22   올스토리   김○○   010-1234-5678   1,069,000  입금      확정
☐ 10/18 11:05   정시      이○○   010-2345-6789     579,000  카드      요청 접수
☑ 10/17 19:40   올스토리   박○○   010-3456-7890     890,000  입금      확정
                                          총계 (2건)  1,959,000원
```

- 자리는 **총액 칸의 가장 아래**다. 표의 `tfoot` 이고 더해진 칸 바로 밑에 선다.
- 아무것도 고르지 않았으면 `0원` 이다. 빈 칸으로 두지 않는다. 고른 것이 없어서 0 인
  것은 오류가 아니다. (ADR-0008 과 같은 선)
- 검색 결과 전체의 합은 **두지 않는다.** 1,000건이면 1,000행을 읽어야 하고, 그것은
  "무제한 `findMany` 금지" 를 어기거나 DB 집계를 켜는 길이다. 좁히는 것은 필터가 하고,
  더하는 것은 선택이 한다. 두 숫자를 나란히 두면 어느 쪽이 자기 질문의 답인지 헷갈린다.
- 건수를 함께 적는다. 금액만 적으면 몇 건을 더한 값인지 확인할 길이 없다.

### 4. 좁히는 수단은 상품 · 연락처 · 결제 방식 세 개를 더한다

기존 검색 폼(고객명 · 기간)에 나란히 둔다. 상태는 지금처럼 칩이다.

- **상품** — 그 상품이 들어간 견적만. `비활성 상품도 선택지에 넣는다.` 끈 상품의 과거
  견적을 찾을 길이 없어지면 안 된다. (ADR-0046 과 같은 선)
- **연락처** — 숫자 부분 일치다. 입력의 하이픈·공백을 떼고 비교한다. 저장은 숫자만이다.
- **결제 방식** — `PAYMENT_METHOD_CHOICES` 에서 만든다. 화면이 값을 손으로 적지 않는다.
  **`미선택` 을 선택지에 둔다.** 고객이 아직 고르지 않은 건이 실무에서 찾는 대상이다.

연락처로 찾는 것도 **개인정보 조회다.** 고객명과 같이 `QUOTE_SEARCHED` 를 남긴다.
검색어는 남기지 않는다. (ADR-0015, ADR-0022)

연락처가 쿼리 파라미터에 들어가는 것은 ADR-0045 가 고객 화면에서 막은 일이다. 관리자
목록은 그대로 둔다. 필터·페이지 이동이 전부 `GET` 링크로 엮여 있어서 한 칸만 `POST`
로 뺄 수 없고, ADR-0015 가 이미 같은 판단으로 고객명을 거기 두었다. 로그인 뒤의
경로이고 그 브라우저는 담당자 것이다. **고객이 읽는 경로에는 이 판단을 가져가지 않는다.**

### 5. 전체 선택은 **버튼**이다. 그리고 그 선택으로는 **지울 수 없다**

ADR-0041 §1 을 이 한 줄로 대체한다. 금지의 이유는 살린다.

- `<button type="button">` 이고 눌린 모양도 켜진 모양도 없다. `aria-pressed` 를 붙이지
  않는다. 선택은 체크박스에만 있다. 라벨은 지금 누르면 일어날 일이다. (ADR-0043 과 같은 모양)
- 판정과 라벨은 `src/lib/select-all.ts` 의 기존 순수 함수를 쓴다. 두 번째 판정을
  만들지 않는다.
- **전체 선택으로 들어온 건이 선택에 남아 있으면 `삭제` 를 열지 않는다.** 사유를 적고,
  지울 건은 한 줄씩 고르게 한다. `모두 해제` 로 선택을 비우면 다시 열린다.
- **`숨기기` 는 그대로 열어 둔다.** 되돌릴 수 있는 작업이고(ADR-0035), 20건을 한 번에
  정리하는 것이 이 버튼을 둔 이유다.

ADR-0041 §4 는 그대로다. **삭제 판정은 서버가 한다.** 확정 건이 섞이면 서버가 전부
거부하는 것도, 그 판정을 화면 비활성에 맡기지 않는 것도 바뀌지 않는다. 위 단락의
잠금은 **화면에만 있는 보조 장치**다. 선택이 어디서 왔는지는 서버가 알 수 없고 알 필요도 없다.

## 이유

### 총계를 서버 왕복으로 만들지 않은 이유

선택이 바뀔 때마다 `POST` 를 보내 Service 가 더하게 하는 길도 있었다. `/api/estimate`
와 같은 모양이라 레이어 규칙에는 깔끔하게 맞는다. 두지 않았다.

체크 한 번에 왕복이 생긴다. 디바운스를 걸면 체크를 누른 뒤 총계가 잠시 낡은 값으로
남고, 그 사이의 숫자는 **어느 선택의 합도 아니다.** ui.md 가 계산 중 상태를 표시하라고
한 것은 금액이 서버에서 만들어지기 때문인데, 여기서 서버가 해 줄 일은 정수 덧셈뿐이다.
있는 값을 더하는 데 네트워크를 끼우면 틀릴 수 있는 지점만 늘어난다.

### 전체 선택을 되살린 이유

ADR-0041 이 막은 것은 **읽지 못한 선택으로 지우는 일**이다. 그 위험은 `삭제` 에서 오고
`전체 선택` 에서 오지 않는다. 그래서 둘을 끊었다. 고르는 편의는 돌려주고, 위험한
작업만 한 줄씩 고르게 한다.

ADR-0026 이 고객 화면의 전체 선택을 없앤 이유는 다르다. 거기서는 체크가 **자기 상태를
거짓으로 말했다.** ADR-0043 이 그것을 버튼으로 풀었고, 여기서도 같은 모양을 쓴다.
목록의 체크박스는 자기 줄만 말하므로 그 문제는 애초에 없다.

### 검색 결과 전체의 합을 두지 않은 이유

담당자의 질문은 "이 조건의 합" 이지 "이 페이지의 합" 이 아니다. 그래서 전체 합이 더
맞는 답처럼 보인다. 그런데 그 값을 만들려면 조건에 맞는 모든 행의 금액을 읽어야 하고,
건수에 상한이 없다. 페이지네이션을 둔 이유가 그것이다.

지금은 상품·결제 방식·기간·상태로 좁히면 한 페이지에 들어온다. 들어오지 않을 만큼
쌓이면 그때 **기간 단위 집계를 따로** 만든다. 목록 화면에 몰래 무제한 조회를 넣는 것과
집계 화면을 만드는 것은 다른 일이다.

## 영향

- `src/lib/quote-sum.ts` 가 새로 생긴다. 순수 함수와 테스트.
- 목록 행에 `totalAmount` 정수가 함께 내려간다. 지금은 포맷된 문자열만 간다.
- `QuoteListFilter` 에 `productCode` · `customerPhone` · `paymentMethod` 가 붙는다.
- `CLAUDE.md` 절대 규칙 1 과 `.claude/rules/ui.md` 의 합계 금지에 이 예외를 적는다.
  예외를 문서에 적지 않으면 다음에 읽는 사람이 규칙을 어긴 코드로 읽는다.
- `.claude/rules/admin.md` 의 "전체 선택 체크박스를 두지 않는다" 를 교체한다.
- 고객 화면은 바뀌지 않는다.
