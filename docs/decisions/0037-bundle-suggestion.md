# ADR-0037. 더 싼 묶음 옵션은 자동으로 바꾸지 않고 안내한다

- 상태: 수락됨
- 날짜: 2026-10-15
- 관련: ADR-0003, ADR-0006, ADR-0008, ADR-0009, ADR-0010, ADR-0025, ADR-0026, `.claude/rules/ui.md`, `.claude/rules/pricing.md`

## 배경

1회성 컨설팅의 `분석 항목` 은 복수 선택 그룹이고 옵션이 네 개다.

| 옵션 | 금액 |
| ---- | ---- |
| 내신 성적 분석 (30분) | 59,000 |
| 모의고사 성적 분석 (30분) | 59,000 |
| 생활기록부 분석 (1시간) | 149,000 |
| 내신 + 생활기록부 분석 (60~70분) | 199,000 |

내신과 생활기록부를 각각 고르면 208,000원이고, 네 번째 옵션은 같은 두 분석을 199,000원에
판다. **체크박스 두 개를 누른 고객은 9,000원을 더 내고, 화면은 그 이유를 말하지 않는다.**
네 번째 옵션이 목록 아래에 있지만, 고객이 세 옵션의 금액을 더해 보고 비교하기를 기대하는 구조다.

`CLAUDE.md` 는 대상이 B2C 이고 "화면에 보이는 금액이 곧 지불 금액" 이라고 적고 있다.
보이는 금액이 틀린 것은 아니지만, 같은 상담을 더 싸게 사는 길이 화면에 있는데도
읽히지 않는다면 그 금액은 고객이 고를 수 있었던 금액이 아니다.

## 결정

### 1. 금액은 건드리지 않는다. 안내만 한다

- 구성 옵션을 전부 고른 선택에 **"묶음으로 바꾸면 얼마가 싸다"** 를 견적 요약에 띄운다.
- 총액은 고객이 실제로 고른 옵션의 합 그대로다. 안내가 금액을 깎지 않는다.
- **할인 규칙을 쓰지 않는다.** 1회성에 할인을 재도입하지 않는다는 ADR-0026 은 그대로다.

### 2. 묶음 관계는 데이터다. `OptionBundle` + `OptionBundleComponent`

- `OptionBundle` 이 묶음 옵션 하나를, `OptionBundleComponent` 가 그 구성 옵션들을 가리킨다.
  `DiscountRule` + `DiscountCondition` 과 같은 모양이다.
- 옵션은 **코드**로 가리킨다. 행 id 는 금액 버전마다 바뀐다. (ADR-0009 와 같은 이유)
- **버전 테이블이 아니다.** `effectiveFrom` 이 없고 수정은 `UPDATE`·`DELETE` 다. (ADR-0025 와 같은 선)
- 금액 컬럼이 없다. 묶음 금액은 그 옵션 자신의 정액이다. (ADR-0026)
- **구성이 한 행도 없는 묶음은 안내 대상이 아니다.** 조건이 비면 항상 후보가 되는
  `DiscountCondition` 과 반대다. 대체할 것이 없는 묶음은 안내할 내용이 없다.

### 3. 판정·절약액·바꿀 선택을 Service 의 순수 함수 하나가 만든다

`src/services/pricing/bundle.ts` 의 `findBundleSuggestions` 가 전부 결정한다.
결과는 계산 응답의 `bundleSuggestions` 로 나간다.

```ts
{
  optionId: string,        // 묶음 옵션
  name: string,            // 그 옵션의 현재 버전 이름
  nextOptionIds: string[], // 바꿀 선택 전체. 화면은 그대로 넣는다
  savingAmount: number,    // 지금 총액 − 바꾼 뒤 총액. 항상 양수
}
```

- 안내 조건: 구성 옵션을 **전부** 골랐고, 묶음 옵션을 아직 고르지 않았다.
- **절약액은 전체 계산을 두 번 돌린 차이다.** 구성 옵션 금액의 차를 따로 빼지 않는다.
- **바꾼 선택이 제약을 위반하면 안내하지 않는다.** 판정에 `validateSelection` 을 그대로 쓴다.
- 안내가 여러 건이면 절약액이 큰 순, 동률이면 옵션 id 순이다. 같은 입력이 같은 순서를 낸다.

### 4. 자동으로 바꾸지 않는다. 고객이 버튼을 누른다

- 안내는 견적 요약 안에 있고, 총액 바로 아래 **항상 보이는** 자리다. 접지 않는다.
- 누르면 선택이 `nextOptionIds` 로 한 번 바뀐다. 체크박스가 그 결과를 그대로 보여준다.
- **화면은 무엇을 뺄지 더할지 계산하지 않는다.** 서버가 준 배열을 넣는다.

### 5. 관리자 화면을 만들지 않는다

어떤 조합을 묶음으로 파는지는 상품 설계다. 금액 운영이 아니다. (ADR-0023 과 같은 선)
등록·변경은 시드와 일회성 스크립트로 한다.

> **보완: ADR-0038.** 이 선이 잘못 그어졌다. ADR-0023 이 막은 것은 그룹 구조이고,
> 틀렸을 때 그 상품을 고르는 방식이 달라지기 때문이었다. 묶음 관계는 틀려도 **안내 한 줄이
> 잘못 뜨거나 안 뜰 뿐이고 금액은 그대로다.** 되돌리는 것도 그 줄을 지우는 것뿐이다.
> 그만한 것을 바꾸려고 코드를 고치고 스크립트를 돌리게 두면 운영자가 손댈 수 없다.
> 가격 규칙 화면에 추가·삭제를 두었다. 수정은 없고, 묶음이 더 싼지도 저장 시점에
> 검증하지 않는다. 안내 여부는 그때그때의 총액 차이가 정한다는 위 결정 그대로다.

## 이유

### 왜 할인이 아닌가

할인으로 두면 **총액이 같아진다.** 208,000 − 9,000 = 199,000 이고 금액은 맞는다.
틀리는 것은 견적서다. 고객은 `내신 성적 분석 (30분)` 과 `생활기록부 분석 (1시간)` 두 줄을
받게 되고, 실제로 파는 묶음은 `내신 + 생활기록부 분석 (60~70분)` 한 건이다.
확정 견적은 수정하지 않으므로(`CLAUDE.md` 6) 그 어긋남을 뒤에서 고칠 방법이 없다.

안내로 두면 어느 쪽을 고르든 견적서가 제공 형태와 일치한다. 묶음을 고르면 한 줄,
따로 고르면 두 줄이다. **안내는 두 선택이 같은 상담이라고 주장하지 않는다.**
더 싼 길이 있다고만 말하고, 무엇을 살지는 고객이 정한다.

### 왜 ADR-0026 이 거부한 "묶음 옵션 바로가기" 와 다른가

ADR-0026 은 `전체 선택을 "묶음 옵션 바로가기" 로 바꿔 남기기` 를 거부했다. 사유는
"입력이 다른 입력을 바꾸는 구조 자체가 문제였다" 다. 이 결정은 그 선을 넘지 않는다.

거부된 것은 **상태를 가진 입력**이었다. 전체 선택 체크는 옵션 목록 안에 체크박스로 살아 있었고,
자기 상태가 다른 입력에 의해 뒤집혔다. 옵션 하나를 끄면 체크가 저절로 풀려서, 고객 눈에는
건드리지 않은 입력이 움직인 것으로 보였다.

여기서 추가하는 것은 **상태가 없는 1회 동작**이다.

| | 전체 선택 체크 (거부됨) | 묶음 안내 (이 결정) |
| ---- | ---- | ---- |
| 무엇인가 | 옵션 목록 안의 입력 | 견적 요약 안의 안내문 + 버튼 |
| 상태 | 켜짐/꺼짐을 가진다 | 없다 |
| 언제 보이는가 | 항상 | 더 싼 묶음이 있을 때만 |
| 누른 뒤 | 입력으로 남아 다른 입력에 뒤집힌다 | 사라진다. 체크박스가 결과를 보여준다 |
| 뜻 | "묶음을 산다" 로도 "전부 켠다" 로도 읽혔다 | 한 가지로 읽힌다 |

누른 뒤에 **안내가 사라지는 것**이 핵심이다. 묶음 옵션이 켜지면 구성 옵션이 꺼져 있으므로
안내 조건이 깨지고, 화면에는 고객이 고른 것과 똑같은 체크 상태만 남는다.
자기 상태를 거짓으로 말할 수 있는 입력이 생기지 않는다.

### 왜 절약액을 전체 계산 두 번의 차이로 구하는가

구성 옵션 합(208,000)에서 묶음 금액(199,000)을 빼면 9,000 이고, 지금 데이터에서는 맞는 값이다.
그 식이 깨지는 자리가 둘 있다.

1. **10원 단위 버림.** 소계에 버림이 걸리면(ADR-0007) 두 총액의 차이가 옵션 금액의 차이와
   달라질 수 있다. 화면에 적는 숫자는 "총액이 얼마 줄어드는가" 이므로 총액으로 재야 한다.
2. **할인.** 구성 옵션을 빼면 할인 조건이 깨질 수 있다. 1회성에는 할인이 없지만,
   묶음을 가진 상품에 할인이 생기면 옵션 금액의 차이는 거짓이 된다.
   할인을 잃어서 오히려 비싸지는 경우까지 포함해 **절약액이 양수가 아니면 안내하지 않는다.**

바꾼 선택으로 계산을 한 번 더 돌리면 이 두 가지가 저절로 맞는다. 계산은 순수 함수라
비용이 없고, 같은 식을 두 군데 적지 않는다.

### 왜 바꿀 선택을 서버가 정하는가

"구성 옵션을 빼고 묶음 옵션을 넣는다" 는 한 줄로 보이지만, 묶음 옵션의 그룹이 단일 선택이면
그 그룹을 비워야 하고, 구성 옵션을 뺀 그룹이 비면 거기에 딸린 그룹의 선택도 풀려야 한다.
(ADR-0010) 이 조건문을 화면에 적으면 **절약액을 계산한 선택과 버튼이 만드는 선택이 달라질 수**
있고, 그러면 안내한 금액이 거짓이 된다.

서버가 `nextOptionIds` 를 그대로 주고 화면이 넣기만 하면 둘이 어긋날 자리가 없다.
`order-input.ts`(ADR-0032)·`option-revival.ts`(ADR-0023) 와 같은 방식이다.

### 왜 해석되지 않는 묶음은 조용히 건너뛰는가

`findRuleSet` 은 할인 조건의 옵션 코드를 찾지 못하면 **예외를 던진다.** 조건을 무시하면
할인이 과하게 걸려서 금액이 틀리기 때문이다. (ADR-0017)

묶음은 반대다. 묶음 옵션이나 구성 옵션이 비활성이면 안내가 사라질 뿐이고, 금액은 고객이
고른 그대로다. 여기서 던지면 **안내 데이터 한 줄 때문에 그 상품의 계산이 통째로 500 이 된다.**
금액을 틀리게 만들지 않는 데이터로 금액 화면을 닫는 것은 바꿔치기가 아니라 손실이다.
그래서 Repository 가 해석되지 않는 묶음을 걸러내고, 순수 함수는 넘어온 id 가 유효하다고 전제한다.

옵션을 비활성화할 때 묶음 행을 지우지도 않는다. 재활성화하면 안내가 그대로 돌아와야 한다.
(ADR-0025 가 설명 행을 지우지 않는 것과 같다)

## 하지 않기로 한 것

- **묶음 할인 추가.** 금액은 맞고 견적서가 틀린다. 위 이유.
- **자동 치환.** 고객이 고른 입력을 서버 판단으로 바꾸면, 체크한 것과 사는 것이 달라진다.
  더 싸지는 방향이어도 같은 문제다. 묶음은 소요 시간이 다른 별개 상담이다.
- **저장 시점에 묶음으로 바꿔 저장.** 저장은 받은 선택을 그대로 다시 계산한다. (ADR-0003)
  고객이 따로 받기를 택했을 수 있다.
- **묶음 옵션을 목록에서 숨기고 안내로만 노출.** 처음부터 묶음을 고르려는 고객의 길이 막힌다.
- **옵션 목록 안에 안내 넣기.** 설명과 섞여 읽히고, 누르는 자리가 옵션 줄 옆에 생기면
  옵션을 고르려던 탭이 선택을 통째로 바꾼다. 안내는 금액 이야기라 요약 패널에 둔다.
- **관리자 묶음 편집 화면.** 상품 설계다. (ADR-0023 과 같은 선)
- **묶음 관계에 `isActive` 컬럼.** 안내를 끄는 것은 행을 지우는 것이다. 이 테이블은
  과거 견적의 근거가 아니다. 견적에 남는 것은 고객이 실제로 고른 옵션뿐이다.

## 영향

- 테이블 두 개가 추가된다. `option_bundle`, `option_bundle_component`.
  기존 테이블·컬럼 변경은 없다.
- `RuleSet` 에 `bundles`, `CalculationSuccess` 에 `bundleSuggestions` 가 추가된다.
  **견적 스냅샷에는 들어가지 않는다.** `save-quote.ts` 가 담을 필드를 하나씩 고르고 있어
  저장 쪽 변경이 없다.
- `calculate.ts` 의 소계·할인 계산이 `price-selection.ts` 로 빠진다. 같은 선택 하나를
  재는 일을 본 계산과 묶음 비교가 같이 쓴다.
- 1회성 컨설팅에 묶음 1건(`V1` ← `NAESIN`, `RECORD`)이 등록된다.
  `docs/pricing-rules.md` 9-1·9-2 의 금액은 바뀌지 않는다. 안내는 총액에 들어가지 않는다.
